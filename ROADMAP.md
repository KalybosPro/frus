# Roadmap

Where frus is, where it's going, and — the point of this document — **what is unclaimed and ready for you to pick up**.

Items are tagged:

- 🟢 **Good first issue** — self-contained, clear success criterion, no deep context needed
- 🟡 **Help wanted** — meaty, well-scoped, needs some familiarity with a subsystem
- 🔴 **Design first** — open a discussion before writing code; the shape isn't settled
- 🔵 **Claimed / in progress** — talk to the maintainers before duplicating

If something here interests you, **comment on the matching issue** (or open one) before starting.

## Where we are

326 milestones in. The framework runs real, non-trivial applications on desktop and Android, and functional ones on the web. What exists is genuinely built, not stubbed: layout, text with IME, drag-and-drop with live reflow, data tables, charts, pickers, navigation with spring transitions, theming, i18n/RTL, accessibility, animation, async effects with typed JSON, and golden-image testing.

What does not exist is everything around it: distribution, tooling, more platforms, and the ecosystem.

## Near term

The things standing between frus and someone else being able to use it.

### Distribution

- 🟡 **Publish to crates.io.** Everything resolves through local `path` dependencies today. This needs real versions, per-crate `README`s, metadata (`repository`, `keywords`, `categories`, `documentation`), a publish order that respects the dependency graph, and a release script. Once done, the `cargo generate` template drops `{{frus_path}}` and becomes `frus = "0.1"`.
- 🟢 **Per-crate `README.md`.** Each crate needs a short one for its crates.io page.
- 🟢 **Pin an MSRV.** There is no `rust-version` in any manifest and no minimum supported Rust version has ever been tested. Find the oldest stable that builds the workspace, put `rust-version` in `[workspace.package]`, and add that toolchain to the CI matrix.
- 🟡 **docs.rs-quality rustdoc.** Crate-level docs with a runnable example on every public crate, and `#![warn(missing_docs)]` turned on crate by crate.

### Web parity

The web target renders and animates but is missing its platform integrations. Each of these is an independent, self-contained job.

- 🟡 **Clipboard** via the async Clipboard API, behind the same interface desktop uses.
- 🟡 **Accessibility.** AccessKit has web support; the semantics tree already exists and is populated. This is a bridging job, not a from-scratch one.
- 🟡 **IME / soft keyboard** on mobile browsers — a hidden input overlay, composition events, viewport insets.
- 🟡 **Live-reload** for the wasm target.
- 🟢 **A proper web example page** — the current `index.html` is minimal.

### Size

Milestone 292 took a release APK from 286 MB to 4.9 MB by building `--release` at all. What is left is real work, not settings.

- 🟡 **Subset the bundled faces at build time.** DejaVu covers far more of Unicode than any one application draws, and the four `bundled-*` features are a coarse instrument next to a `pyftsubset` step over the glyphs a build actually references. This is where the next megabyte is, and it needs a tool in the build.
- 🟢 **A size regression check in CI.** Nothing notices today if the floor doubles. Build `frus-hello` for `aarch64-linux-android` in release, compare the stripped `.so` against a committed budget, fail on a jump.
- 🟢 **Document `--split-per-abi`-style packaging.** The examples build `aarch64` only; an application targeting more than one ABI wants a split rather than a fat APK, and nothing says so.

### Quality

- 🟢 **Clear the clippy backlog — done, milestone 298.** 71 warnings, now zero, and CI runs `cargo clippy --workspace --all-targets -- -D warnings` as a **blocking** check. Six `too_many_arguments` carry a targeted `#[allow]` with the reason at the site; everything else was rewritten.
- 🟢 **Format the tree — done, milestone 298.** One `cargo fmt --all` commit over 40 files, on its own, and the fmt check is **blocking** now.
- 🟢 **Widen golden coverage — done, milestones 296 and 297.** 58 of the 86 widget modules had no pixel test at all; **all 86 have one now**. 296 added 27 goldens for the widgets whose picture follows from their arguments; 297 added `frus_test::Stage`, a harness that holds the retained state and steps the frame loop the way the shell does, and 12 more for the ones whose picture is a gesture in flight — a swipe half done, a pull past the top, a glow, a page between two pages.
- 🟢 **An overlay belongs to its screen — done, milestone 326.** The red item found on a device: an app bar's overflow menu, left open while choosing "Settings →", stayed drawn over the screen that replaced it. Neither obvious explanation was right — no retained state leaked, and the outgoing screen had not left the tree (during a transition it is genuinely still in it, and once the spring settles the menu goes with it). Reproducing it through `Application::view` and printing the item's position every frame showed the actual cause: it never moved. `process_overlays` runs after both screens and paints above the **whole window**, so a deferred overlay outranks the screen drawn on top of its owner; and the transition is parallaxed, so the outgoing screen travels only 30 % of the width and the anchor never leaves. A screen on its way out now takes its floating layers with it (`children[1]` is always the destination — on a push, on a pop and under a back gesture). Reading that code turned up a second bug: the auto-flip that keeps a menu inside the window would drag an overlay whose anchor had genuinely left the window back into view, barrier and all, which a portal in a horizontally scrolled row hits with no navigator involved. The report's other half — the menu reappearing on returning home — was the application's: `Msg::Push` dismissed the drawer and the popup menu and missed the overflow.
- 🟢 **A tap on a dismissible row did nothing — done, milestone 327.** Found on the device as "the task row's avatar does not open the task". Of the two candidates, the hit box was cleared first: a probe sweeping the window found the target at exactly the 30 px the avatar is drawn at, topmost, resolving to the right message. The gesture arena was the whole of it. A press on a dismissible row prepares a swipe that engages only past a threshold, and the release told a tap from a drag by matching against a list of the four gestures that behave that way — `Scroll`, `Pan`, `Reorder`, `Item` — with `Dismiss` missing. So the press recorded the widget, `pointer_up` returned before the click path, and nothing was ever told. It shows only when the list is too short to scroll, because a scrolling list claims the press as a `Scroll` first, which is why the bug arrived looking intermittent; reading the routing, a pointer reaches the swipe branch unconditionally, so on desktop every click on such a row was swallowed. The list is now `gesture_was_a_tap`, named and tested in both directions. Confirmed on the device: the avatar opens the task, the checkbox (dead for the same reason, never reported) toggles, a short swipe springs back without navigating and a long one still dismisses. Milestone 321's centring is verified in passing.
- 🟡 **A long task label pushes the row's delete button out of the card.** Found on the device while restoring the demo's tasks in milestone 327. The row is `[avatar, checkbox, label, spacer, ×]` with nothing bounding the label, so a long one grows past the spacer and evicts the trailing action rather than ellipsising. Read one way it is the demo's to fix — the reference gives such a title an expanding box. Read another, a row that silently drops a trailing control instead of clipping wants a framework answer. Decide which before fixing it.
- 🟢 **Nothing checked a painted colour against the token that asked for it — done, milestone 331.** Three milestones running (328, 329, 330) were colours that did not survive the trip to the screen, each one sRGB↔linear conversion in the wrong place, each found by accident. Nothing caught them because the defect never reaches the layer anything watches: the widget builds the right colour, the scene primitive carries it, and the golden is regenerated from the same broken pipeline so it agrees with itself forever — 110 of them agreed with milestone 330's text for as long as text has existed. `crates/frus-test/tests/painted_colours.rs` renders a known colour through each of the four surfaces that paints one (quad, glyph, path, image tint — they convert in four different places, which is exactly what 330 tripped over) and reads the pixel back, naming the slip when it fails. All four shown to bite independently. Left: translucency (still linear, tracked separately), gradients, shadows and the compositor's layer path.
- 🟡 **Everything translucent except the disabled tokens still blends in linear light.** Milestone 328's finding: the reference's opacity numbers assume an sRGB blend, and an `Rgba8UnormSrgb` target makes the hardware decode to linear, blend and re-encode — correct physics, ordinary wgpu, and a whisper that paints at roughly what 33 % would give. Milestone 329 took the **disabled** tokens out of the pipeline's hands (`disabled::over_surface` resolves the blend in sRGB and hands the GPU an opaque colour, which is what "a disabled control flattens; it does not fade" always meant), so the controls this was found through are fixed. What remains is scrims, ink, state layers, elevation overlays and any colour an application fades itself — none audited, none reported. The pipeline route stays open: a non-sRGB surface format with the shaders' `srgb_to_linear` dropped, which reaches four shaders, the glyph upload, the image path, the offscreen path and every golden. `crates/frus-test/tests/blending.rs` pins the current behaviour so that change stays deliberate.
- 🟢 **Dark `secondary_container` was eight tones below the reference — done, milestone 329.** Tone 22 where the reference puts it at 30, and where the light scheme's already sat: under the disabled fill it has to beat, so a slider's rail and a selected segment read as unavailable. Written and reverted in 328 because validating it meant reading goldens against a disabled fill itself 14 tones adrift; fixed here, in the order 328 asked for — blend, then palette, then read the pictures once. Left: the rest of that dark family runs low (`secondary` is tone 69 against the reference's 80), which collides with nothing and is an aesthetic call.
- 🟢 **A checkbox's box and a radio's ring were a container-edge role — done, milestone 332.** Both were `outline`; both are the **mark**, not a container with something inside it, so both take an *on* colour — which `disabled.rs` has said in prose since milestone 322 while the enabled branch of each control said otherwise. The roadmap's `on_surface` was half right: the reference resolves the side per state, `on_surface_variant` at rest and the full `on_surface` under a finger, a pointer or focus, and we had one colour for all of them. The radio came in with it because it is the same rule and the same wrong role; `RadioOption` being its own widget, it receives its own `Status`, so hovering one option lifts that ring alone. Dark moves `(141, 145, 153)` → `(150, 156, 168)`; in light the two roles are five values apart and only a 20×20 region moved. Left: no `error` state on a checkbox at all, press not distinguished from hover, and neither control has a theme entry yet.
- 🟡 **Make the goldens a required check.** The step stays advisory, and an advisory check went red for five milestones without anyone noticing (J294). The reason recorded here — "lavapipe rasterises differently from hardware" — is not the real one: the goldens are *blessed* under lavapipe too (llvmpipe in WSL is the only adapter there), so both sides run the same rasteriser. What actually differs is its **version** — mesa 25.2 locally against whatever `apt` gives ubuntu-latest. So the job is either to pin the rasteriser in CI (a container image, or a mesa PPA) and drop `continue-on-error` outright, or to measure the version-to-version drift and absorb it through `assert_golden_with`. Pinning is the honest one; a tolerance guessed without measuring is a number nobody can defend.
- 🟢 **`Scaffold` should not scroll the body — done, milestone 321.** Every body was wrapped in a `Scroll` unconditionally, so an application could not say *this screen does not scroll*, and a screen that fitted still carried an offset, a physics and a set of edge effects it never asked for. That wrapper is what gave the home page a scrollable to light a glow on; milestone 316 stopped it *acting*, which was never the same as it not being there. The body is placed loose and top-aligned in the room the bars leave it now, as the reference's is — a body that wants all of that room says `.flex(1.0)`, and a body that may overflow goes inside a `Scroll` or a `List`. The keyboard-avoidance logic moved with it and came out simpler: the bottom clearance is a sibling of the body rather than padding inside a viewport. All three demo screens using a `Scaffold` answered the migration differently, which is the argument for the change. Left: with the scroller inside the body rather than around it, the app bar is **further** from knowing when content has passed beneath it — see `scrolledUnderElevation`, below.
- 🟢 **A live outline can be told from a disabled one — done, milestone 325.** Open since milestone 320, promoted by 324's device pass, and settled by arithmetic rather than by a screenshot: a disabled outline is `on_surface` at 12 % over the surface, and both shipped palettes put `outline_variant` within **2.2 tones** of it in dark and **0.5** in light, where the reference separates them by about ten. `ColorScheme::from_seed` had it right all along — tones 60/30 dark, 50/80 light — so only the two hand-written schemes had drifted, and taking those tones from each palette's own neutral-variant family lands within a few units of the reference's baseline colours. Raising the token was half of it: thirteen `theme.border` call sites were drawing **separators** rather than control edges (chart gridlines, a nav bar's hairline, a drawer's edge) and moved to `outline_variant`, and a slider's rail moved to a container tone because it is a filled track, not an edge. Sixty-two goldens moved and all sixty-two were read; the largest visible win was not the disabled states but the outlined text fields, whose borders had been effectively invisible. A tone-gap test now covers both shipped schemes and three seeded ones.
- 🟢 **Every control that can be pressed can be disabled — done, milestone 324.** `Rating`, `Stepper`, `Menu`, `Tabs` and `Pagination` finish the sweep 320 started. Reading the golden is what earned this one: flattening a rating's stars to one grey destroyed the score, and a disabled page strip showed six identical pills with no current page — which turned out to be `Button` flattening too far. The reference is explicit that a text button's background is transparent in every state and that an outlined one keeps its outline at 12 %, so a disabled button loses its **accent**, not its **shape**; `IconButton` had the same missing outline. `Stepper` and `Pagination` also stopped lying about their bounds — a button at the end of its range is disabled now rather than clamped or merely silent. Along the way `impl Widget for Box<dyn Widget>` turned out to be missing `build_themed` and `repaint_boundary`, latent because every walk takes `&dyn Widget`, and now guarded by the same reflection test that guards the transparent wrappers. Left: no single disabled item anywhere, and `enabled` is still a flag per widget rather than the shared resolver the reference uses.
- 🟢 **The last two form controls — done, milestone 323.** Milestone 322 named five controls a form is mostly made of and did three; `Slider`, `RangeSlider` and `Dropdown` finish it. The slider is why 322's guard covers drag and key hooks at all — it answers a drag on the track, a drag on each thumb and four keys on a focused thumb, none of them a tap — and **the guard caught the omission it was written for**, a `RangeSlider::semantics` left telling a screen reader it was live. A disabled `Dropdown` is never open, whatever it was told, since a floating menu over a header that answers nothing traps a press and returns no message. It also corrected 322's own documentation: outlines split the same way everything else does, a container's outline taking 12 % and a checkbox's ring 38 %, because the ring is the mark rather than a container around one. Left: `Rating`, `Stepper`, `Menu`, `Tabs` and `Pagination`, none of them a form control.
- 🟢 **One disabled state, shared — done, milestone 322.** Milestone 320 called `enabled` a flag per widget; the count was worse than that. Five widgets had it with `on_surface.fade(0.12)` and `.fade(0.38)` written out by hand in each, and **ten had no way to be disabled at all** — `Checkbox`, `Switch`, `RadioGroup`, `Slider` and `Dropdown` among them, which is most of what a form is. `frus_widgets::disabled` holds the rule once, and the split turns out to be **container against content** rather than one rule per widget: the switch proves it by taking both halves, its track at 12 % and its thumb at 38 %. A third colour covers a mark drawn *on* a disabled fill, since 38 % on 38 % is invisible. `Checkbox`, `Switch` and `RadioGroup` can be disabled now, and a source-reflection guard insists every widget carrying the flag consults it in each hook it implements — drag and key hooks included, a slider being dragged rather than tapped. **It failed on its first run**, on 320's own delete cross: tap gated, tab order and screen reader not. Left: seven controls still cannot be disabled (`Slider` first), no single disabled option, and no theme entry for the three new ones.
- 🟢 **The gap three milestones wrote down — done, milestone 320.** Milestones 312, 313 and 314 each ended with the same line: the widget cannot be disabled. `Chip` and `SegmentedControl` take `enabled(false)` now, and it turns off more than a colour — the press goes nowhere, no ink, out of the tab order, announced as disabled rather than falling silent, and a chip's **delete cross goes dead with it**, which would otherwise have been the one live control on an inert thing. Disabled **flattens** to `on_surface` at 12 % under a label at 38 % rather than fading the accent: a pale accent reads as *quietly selected*, a grey one reads as *unavailable*. A golden holds each pair side by side, because 312's invisible delete cross survived precisely by never being drawn. Left: no single disabled segment, and `enabled` is still a flag per widget rather than the shared state every control could hang off.
- 🟢 **A widget that builds from the ambient theme — done, milestone 319.** The `caller ?? theme ?? framework` chain reached painted properties (309) and layout (310) and stopped at anything decided while a composition was being **assembled**: `AppBar::build()` never saw a theme, and `center_title` picks which children exist rather than how they look. `ThemeBuilder` takes `theme → widget` and builds on the way down in the layout pass, through a new `Widget::build_themed` hook. Unlike `LayoutBuilder` it keeps **retained state** — a theme is the same frame to frame where a box is not, so the subtree keeps its positional identity and an app bar inside one keeps its overflow menu open. `AppBar` is the first consumer: `center_title` now resolves `caller ?? theme ?? platform`, and `AppBarTheme` carries the title's type, the colours, the elevation and the height. Left: `Scaffold`, `NavBar`, `Drawer` and the pickers are still assembled before a theme is in hand, and `children()` is not self-healing — a traversal that skips `build_themed` sees an empty node.
- 🟢 **Chrome that changed shape — done, milestone 318.** `AppBar` sized itself to its content, so every screen was a slightly different shape and the page moved the moment an action appeared. It is the reference's fixed 64 px now, with the title at `title_large` and the actions at `label_large` — its actions are text buttons. Left: the theme middle term (above), no scrolled-under elevation, and elevation is a number the caller gives rather than something the framework knows.
- 🟢 **The field everybody types into — done, milestone 317.** `TextInput` had nine hardcoded numbers and no way to change any of them. The measurements come from the reference now, including two that are more than numbers: an outlined field's padding is asymmetric (20 above, 12 below) because its label floats *onto* the top border and the top has to give it room, and the label **scales** by 0.75 rather than taking a second fixed size — a field told `size(32)` used to get a 13 px label. Both of the reference's fields exist at last: `filled()` is a tinted container with one line under it, not the outlined box wearing a tint. Fourteen settings per call or through `TextInputTheme`, and `enabled` — the gap milestones 312, 313 and 314 each recorded — which dims to 38% and leaves the field readable, unfocusable and inert. Left: padding and icon size still resolve `caller ?? framework` only (the geometry paths run without a theme), no bare underline field, and no counter, `maxLength` or prefix/suffix *text*.
- 🟢 **One gesture, one axis, one area — done, milestone 316.** Three reports from a phone, one question the shell had never asked. A finger scroll applied both deltas to the area under it, so a page scrolling down drifted sideways the whole way; a scrollable elsewhere has **one** axis and an arena decides between them, so the axis is claimed once at the threshold and held to the end of the drag, the release included. The area is claimed there too — the press walks the whole stack of scrollables under the finger, so a sideways strip stops swallowing a drag straight down the page behind it. And an area whose content **fits** now takes no drag at all, which is the rule stated outright in the reference (*only if there is content outside the viewport to reveal*): the home page stopped lighting an end-of-content glow at edges it does not have, and a dead scrollable stopped swallowing presses. Left: no hand-off of the *remainder* to the page behind when an inner list hits its end, `Axis::Both` is still one node with one physics, and the claim compares components rather than racing two slops.
- 🟢 **The missing icon button — done, milestone 315.** Two milestones in a row patched the same thing at seven call sites: a button holding one glyph in a box sized for a word. `IconButton` is the reference's — 40×40, circular, no fill — with four variants, a selected state, and a `label` because an icon says nothing to a screen reader. It takes a bundled icon or a glyph, since the set has thirteen shapes and applications draw more. Left: no `selectedIcon` pair, no tooltip, and an icon set that is still thirteen shapes.
- 🟢 **The segmented control was three buttons — done, milestone 314.** A filled button for the chosen segment, outlined ones beside it, two pixels apart, one setting: the same finding as `Tabs`, in the widget next to it. It is one control now — one outline with stadium ends, a hairline at each division, the chosen segment filled with the tonal container and carrying a checkmark. The fill sits *inside* the outline so it does not rub it out, and every segment takes the width of the widest so renaming one does not move the others. Eleven settings per call or through `SegmentedTheme`. Left: no multiple selection, no icon of your own, and nothing can be disabled — the third widget in three milestones missing `enabled`.
- 🟢 **Every button had a shadow — done, milestone 313.** Three variants, a hardcoded label size, and a drop shadow under every enabled button whatever it was: the reference's elevated button drawn five times over, and an emphasis order in which nothing is quiet. The five are here now (filled, tonal, elevated, outlined, text) with `Danger` kept as frus's own, along with the reference's measurements — 64×40 minimum, a stadium whose radius follows the height, `label_large`, 24 px either side — and ten settings per call or through `ButtonTheme`. It exposed the missing widget: four of the framework's own buttons hold a single glyph and want an icon button, which does not exist yet. Left: no icon button, no leading icon, no lift on hover, and `SegmentedControl` builds itself out of buttons the way `Tabs` used to.
- 🟢 **The chip was a pill — done, milestone 312.** Two builders, a Material 2 stadium filled with a made-up colour, no press, no selection, no icon. It is the reference's chip now: 32 px, an 8 px radius, an outline that gives way to a fill once selected, a checkmark, a leading icon, and thirteen settings per call or through `ChipTheme`. The reference's four chip classes differ by affordance rather than shape, so they are builders rather than types. It turned up a delete cross painted in a transparent colour, visible only under a pointer — which on a touch screen is never. Left: no elevated variant, no avatar, no `enabled`.
- 🟢 **`Tabs` was a row of buttons — done, milestone 311.** The selected tab was a filled button and the others were outlined ones, which is not a tab bar: a tab bar is labels with a sliding indicator under the selected one and a hairline under the lot. Both of the reference's variants are here, with its measurements read out of its source rather than remembered, and all ten of them settable per call or through `TabsTheme`. The indicator slides because the runtime already tweens a per-widget value — the same mechanism a switch's thumb uses. It turned up a real defect: a widget animated through `anim_target` was painted at zero in any frame the runtime had not advanced, so a `Switch` rendered on its own came out off. Left: no scrollable bar, no icons in a tab, and no bar without a panel.
- 🟢 **Themes compose — done, milestone 310.** Milestone 309's defaults could be said once, for everything: one theme per frame meant a dark panel on a light page had to be written out property by property inside it. `Themed` replaces or tweaks the theme for a subtree, the way the reference has always done it, and reaches **layout** as well as paint — the swap happens in the layout walk and in the relayout cache's fingerprint of that same walk. A deferred overlay carries the theme it was declared under, so a dialog opened from a themed section does not come out in the application's colours. Transparent-wrapper forwarding became a macro checked against the trait, which promptly found two hooks `Keyed` had never forwarded. Left: direction is not mirrored per subtree, and a theme cannot animate between two states.
- 🟢 **Per-widget theme defaults — done, milestone 309.** Three milestones in a row ended on the same missing piece: an application could override one card, one divider, one splash, and had no way to say *every one of them*. `Theme.widgets` is the reference's middle term, `caller ?? theme ?? framework`, with every field an `Option` so an empty theme is indistinguishable from none. The part that was not obvious is that a theme has to reach **layout**, not only paint — a divider's height and a card's margin are the settings people actually want — which `Widget::style_themed` does without touching the ninety widgets that do not care. The relayout cache fingerprints the themed style, so a theme swap recomputes rather than replaying. Left: only four widgets are wired; themes do not compose, so a dark card on a light page is still not expressible.
- 🟢 **The card was three cards at once — done, milestone 308.** `Card` had a padding and a child, and wrote its whole appearance into `paint` as literals: a shadow *and* an outline, which is none of the reference's three cards. It has the three now (`Elevated`, `Filled`, `Outlined`), and the outline belongs to exactly one. Elevation, colour, rounding and margin are the caller's, and elevation is a **height** — blur and drop both derived from it — rather than a blur radius under another name. Left: no `clipBehavior`, and a card still cannot be tapped, which milestone 306's ink now makes cheap.
- 🟢 **A sweep for what does not match the reference — first batch, milestone 307.** After 305 turned up a widget deciding something the reference leaves to the application, the instruction became retroactive: audit what is already written, not only what is being added. Clean so far: scroll physics, the refresh indicator's two constants, `Dismissible`'s default direction, and no second widget measuring its own width to change shape. Corrected: `Drawer` was 280 px where the reference is 304, and the constant was unchangeable (`Drawer::width` now overrides it); `Divider` was a unit struct with no fields at all, drawing its line by filling its one-pixel box, where the reference has a box height *and* a line thickness (16 and 1), indents that inset the line rather than the box, and a colour. Correcting the drawer's width broke an RTL test that had been asserting the **reverse** of the behaviour and passing on an overflow artefact. Left: a drawer wider than its window overflows instead of shrinking; no `VerticalDivider`; and the theme carries no per-widget defaults, so an application can override one divider but cannot set them all at once — the same gap `splashFactory` ran into.
- 🟢 **Ink, and a title that knows where it is — done, milestone 306.** There was no ink ripple at all: pressing a surface changed a colour and nothing moved. The reference's `InkRipple` is transcribed — five durations, a radius that swells for a second under a held finger and finishes in 225 ms once it lifts, a fade-out with a dead zone for its first three fifths, `ease` on radius and drift alike — behind a new `InkWell`, `Widget::ink`, and `Runtime::ink`, with `Button` taking ink. The splashes are wired into the repaint-boundary cache, so one inside a cached subtree animates rather than freezing. In the same pass, `AppBar` stopped deciding that no platform centres its title: the default follows the target now, Apple's platforms centring while there are fewer than two actions, with `center_title` overriding either way. Left: the reference's other two ink features, `InkHighlight` (the steady wash under a held surface) and `InkSplash` — both needed before a `splashFactory` equivalent means anything.
- 🟢 **A scaffold decides nothing on its own — done, milestone 305.** `Scaffold` measured its own width and swapped a bottom bar for a side rail past the `Compact` threshold, with no parameter to ask it otherwise — so turning a phone to landscape relocated the navigation, found on a device. The reference has one navigation slot, at the bottom, with no breakpoint in it. The navigation is a bottom bar at every width now; `NavPlacement::Rail` pins a rail, fixed; and navigation that follows the size class is `NavScaffold`, a separate shell named for it. Left: `NavScaffold` is thin next to `Scaffold` — destinations and a body, no app bar, drawer, FAB or sheets — so wanting adaptive navigation *and* the rest means building the outer shell by hand. Either it grows the slots, or `Scaffold` learns to take a pre-built navigation widget in a slot, the way the reference's bottom slot takes any widget.
- 🟢 **A real async runtime — done, milestone 303.** `Command::perform_async` existed, and natively it was a thread per effect plus `pollster::block_on`, with **no reactor** — so a future that waited on a timer or a socket parked its thread and nothing ever woke it. Asynchrony was in the type system and absent underneath it. There is now one executor on four workers, each running it inside `async_io::block_on`, and every asynchronous effect and every subscription is a task on it. New: `Command::after`. Left, and this is the interesting part: **accept a runtime instead of owning one** — an `Executor` trait an application implements, so a codebase already running tokio hands it over and the whole HTTP ecosystem becomes reachable; and **subscriptions as streams**, since `Subscription` still has exactly one kind, `Every`, while a WebSocket or a file watcher is now expressible.
- 🟢 **Pictures in the README — done, milestone 304.** A GIF of the demo crossing four screens, four stills and one photograph of a phone, plus the tool that renders them (`--features shots`), so a picture is regenerated after a change rather than left to go stale. The starting issues live in `.github/issues/` with a script that opens them.
- 🟢 **Benchmarks — done, milestone 299.** `crates/frus-bench`: `build_ui`, text measurement and wrapping, and batch planning, on shared fixtures, under the release profile. `cargo bench -p frus-bench`; CI runs `-- --test` so they cannot rot. The baseline and what it found are in `docs/milestone-299.md`. Left: nothing measures the **GPU** side of a frame, only the CPU side.
- 🟢 **Fix the broken intra-doc links — done, milestone 298.** Twelve of them: links to private items, two to types that never existed (`ClipRect`, `RepaintBoundary`), one to an entry point renamed away, and five in `form`'s module docs that resolve only when written in full. `ValueAnim` became public, since it is the type of a public field. The strict rustdoc pass is **blocking** now, and it turned up an unparseable `ignore` code block behind them.

## Medium term

### New platforms

- 🔵 **iOS shell.** The most valuable single contribution available. `frus-shell` is the only crate that would change: a `UIViewController` host, Metal surface via `wgpu`, touch input, IME, lifecycle, safe-area insets. The layering is designed for exactly this, and Android is the worked example to follow.

  **Groundwork landed** (see `docs/milestone-276.md`): `frus-shell` now has named platform `cfg` aliases (`desktop` / `android` / `ios` / `web`) via its `build.rs`, so iOS no longer falls silently into the desktop branch, and a `run()` entry point exists behind `#[cfg(ios)]`. An advisory CI job builds for `aarch64-apple-ios-sim` and `aarch64-apple-ios`. What remains is the actual platform integration — lifecycle, safe-area insets, IME/soft keyboard, `os_log`, UIKit accessibility, and `.ipa` packaging.
- 🔴 **Native macOS shell.** winit already covers macOS as a desktop target; a native shell would be about menu bar, window chrome, and platform conventions rather than rendering.

### Framework depth

- 🟡 **Text rendering edge cases.** Bidi runs, complex scripts, font fallback chains, emoji, vertical metrics. Real bug reports welcome here.
- 🟢 **`Scaffold` and `body` — reviewed, milestone 288.** `extend_body`, `extend_body_behind_app_bar`, `resize_to_avoid_bottom_inset`, `window_insets`, a leading `drawer` beside the trailing one, and `persistent_footer`. The FAB gained a **location** in milestone 290 — three ends × float or docked.
- 🟢 **A bottom app bar with a notch — done, milestone 291.** `BottomAppBar` in the scaffold's bottom slot, cut around a docked FAB by the scaffold, which is the only party that knows where both are. Left: the bar has no elevation or surface tint, for the same reason the app bar has none.
- 🟢 **The renderer composites in scene order — done, milestones 294 and 295.** It used to draw one pass per kind — rectangles, then images, then paths, then text — so *every* path covered *every* rectangle in the frame, wherever the two sat in the scene. Found on a device in milestone 291 (a filled button on a notched bar); it applied to `CustomPaint`, the charts, `ClipPath` and the overscroll glow just as much. Primitives are now given a **level** from what they cover, and a level costs one draw call per kind it holds — a twelve-row list is 3 draw calls, where ordering primitive-against-primitive would have cost 25. Text was left out of the plan in 294 and folded in by 295, once `Primitive::Text` learned to carry the box it was laid out in. `frus_gpu::draw_calls(scene)` reports the cost. Left: a primitive's footprint is its widget's box, so text over a wide, mostly-empty label costs a level it need not; tightening it to the shaped extents wants the measurement to come back from the text painter.
- 🔴 **A widget cannot measure its children, nor describe anything to its subtree.** Children are built by the application *before* the widget that holds them sees them, so a container can neither ask how big they are nor put an ambient value where they would read it. The reference builds lazily and does both. Three known symptoms, all deferred for this one reason: the FAB's height must be **declared** to dock it (`fab_size`, milestone 290) and its `*Top` placements are missing for want of the app bar's height; `AppBar` is a builder rather than a `Widget` because it needs the available width before it can decide anything; and a scaffold cannot tell an extended body what it is running under, so that body pads its own content by hand. Wants a design — lazy children, or a resolution pass between build and layout — not a parameter.
- 🟢 **`AppBar` is a builder, not a `Widget`** — it must be finished with `.build()` because it needs the available width before it can decide anything. Every other widget in the framework *is* a `Widget`. Revisiting it is an API change with call sites, not a fix.
- 🟢 **The app bar's title carries no `Role::Heading`.**
- 🟢 **`NavBar` shrinks around its back button** when its parent gives it no width (found by milestone 296's first golden of it). Its `paint` centres the title in `bounds`, which only makes sense at full width, but its `style` asks for `Dimension::Auto`, so with nothing to fill it hugs the button and paints the title underneath. Every screen happens to give it a width, which is why it has never shown.
- 🟢 **A wrapping text that is shrunk to fit reported one line's height — fixed, milestone 289.** The diagnosis recorded here (measure-pass ordering) was wrong: the cause was half a pixel. Text measurements now round up, so the box the layout rounds to is one the text still fits in. Left, and general: the layout engine rounds every box to whole pixels while the reference does not, so anything that measures itself must round up too.
- 🟢 **Scrolling physics — done, with two loose ends.** `ScrollPhysics::{Bouncing, Clamping}` with the platform's own fling curves, a real rubber band and per-app / per-area overrides (`docs/milestone-277.md`); a fitted velocity estimate (`docs/milestone-278.md`); the overscroll glow, device-verified (`docs/milestone-279.md`) and rebuilt as an actual **fade** in milestones 301 and 302 after a second device report — it was a flat fill, and a hard curved edge across the page reads as the page being bent rather than as light. Paths carry a gradient now, straight or radial. Left: the **stretch** overscroll effect newer platform versions use instead of a glow (needs a render-target effect), and the second bouncing deceleration profile.
- 🟢 **Cache text measurement — done, milestone 300.** Milestone 299 found that **three quarters of the cost of building a frame was `frus_text::measure`**, re-shaping every string through cosmic-text on every call for strings that had not changed. A cache keyed on `(text, size, weight, italic, max_width)` — with the weight and style **resolved**, so a Medium asked for on a family that only ships Regular hits the same entry as the Regular — took `measure/line` from 16.3 µs to **79 ns**, and took building a twelve-row frame from **4.1×** the cost of the same tree with no strings in it to **1.20×** — text is a sixth of a frame now, where it was three quarters. Eviction is two generations with a promotion on hit, so a string still on screen never falls out and one that has gone leaves with its generation; registering a font empties the cache, an answer from before that being wrong rather than stale. Left: the batch planner is still O(n²), and nothing measures the GPU side of a frame.
- 🔴 **Rebuild memoization.** `view` rebuilds the whole tree each frame. Milestone 299 sized it: the same tree with every string replaced by a fixed box costs a quarter as much, so rebuilding is real but it is the *small* half — measure text first. Wants a design, not a parameter.
- 🟡 **The batch planner is O(n²).** Each primitive scans the levels for something it overlaps: 80 primitives plan in 4.7 µs, 1302 in 597 µs (16× the primitives, 127× the time). About 4% of a 60 Hz frame at 1302, so not urgent — but it grows the wrong way, and milestone 294 should not have implied the plan was free. Wants a spatial index, or levels that carry a bounding box per kind.
- 🟡 **Renderer batching.** Fewer draw calls for scenes with many small primitives; atlas the common shapes.
- 🟡 **More widgets.** The catalogue is broad but not complete. Landed in milestone 280:
  the ambient surface description (`MediaQuery`, `SafeArea`) and the widgets that withhold
  part of the frame (`IgnorePointer`, `AbsorbPointer`, `Visibility`, `Offstage`,
  `ExcludeSemantics`). Still unclaimed, roughly in order of how often they are reached for:

  - 🟢 **Pull-to-refresh — done** (milestone 281): `Refresh`, device-verified under both
    physics. Left: the same machinery on the **bottom** edge for load-more, and a way for
    an application to start the indicator itself.
  - 🟢 **Swipe-to-dismiss — done** (milestone 282): `Dismissible`, with the shared-gesture
    arbitration that lets it live inside a list. Left: a confirmation step (an undo window
    needs the message to be able to refuse) and cross-axis drift. The on-device check is
    **done** (2026-08-12).
  - 🟢 **A paged view — done** (milestone 283): `PageView`, virtualised, snapping on the
    milestone-277 physics, with `page`/`on_page_changed` binding both directions to one
    number, device-verified in both directions. Left: per-page transformations (parallax,
    depth), padded ends below a `viewport_fraction` of 1, and keyboard paging.
  - 🟢 **Shared-element transitions — done** (milestone 286): `Hero`, device-verified.
    The "two trees" half turned out to be free — the navigator already holds both screens
    in one frame. Left: a curved flight path, a cross-fade between the two contents, and
    shared elements that move *within* a screen rather than between routes.
  - 🟢 **The constraint boxes — mostly done** (milestone 284): `SizedBox`,
    `ConstrainedBox`, `Intrinsic`, `OverflowBox`, and `max_width`/`max_height` on `Style`.
    Two are left, and both need something the layout does not yet surface:
    **`LimitedBox`** needs to know whether the incoming constraint was *unbounded*, which
    taffy owns and never tells a widget; **baseline alignment** needs the text measurement
    to report a baseline, which the measure hook cannot return.
  - 🟢 **A general drag-and-drop pair — done** (milestone 285): `Draggable` /
    `DragTarget`, with a `u64` payload, a ghost lifted out of the frame, and a lift that
    yields to any scrollable under it (`long_press()` inside a list). Device-verified.
    Left: auto-scroll at a viewport's edges while carrying, a typed payload, a fly-back
    on a refused drop, and migrating `Kanban`/`Table` onto it.
  - 🟡 Rich text editing, video, maps, virtualized lists for very large datasets.
- 🔴 **Router / deep linking.** `navigator.rs` handles in-app navigation; URLs, deep links, and browser history are not modelled.
- 🟡 **State persistence.** A blessed way to save and restore app state across lifecycle transitions.

## Long term

The original brief aims at a full framework, not just a UI toolkit. These are real goals, not yet real work:

- **Plugin system** — a stable ABI for third-party platform integrations (camera, sensors, storage), with the thin-native-adapter rule enforced.
- **FFI story** — embedding frus in an existing native app, and calling native code from frus.
- **Package/ecosystem conventions** — how a community widget library is published and discovered.
- **Static analysis** — lints specific to frus's architecture (impure `update`, hardcoded styling, misplaced platform code).
- **Documentation site** — the milestone notes are excellent raw material, but they are unindexed and unsearchable outside `grep`.

---

## Non-goals

Stated so nobody spends a weekend on them:

- **A DSL or markup language.** Rust with builder methods and the `column!`/`row!` macros is the API. No `.frus` files, no macro that reinvents syntax.
- **A bespoke CLI.** `cargo` is the tool. `cargo generate`, `cargo apk`, `wasm-bindgen` are existing tools; we don't wrap them in `frus doctor`.
- **A software rasterizer.** `wgpu` covers every target we care about.
- **Framework logic in another language.** Non-Rust code is limited to thin platform adapters with no logic of their own.
- **Cloning another framework's API surface verbatim.** We port what works and fix what doesn't. "Framework X does it this way" is a starting point in a discussion, not an argument that ends one.

## How to pick something up

1. Find an item here or in [issues](https://github.com/KalybosPro/frus/issues).
2. Comment saying you're taking it. If there's no issue, open one first — especially for 🔴 items.
3. Read the relevant part of [ARCHITECTURE.md](ARCHITECTURE.md) and `grep docs/` for prior decisions in that area.
4. Build it, test it, and follow [CONTRIBUTING.md](CONTRIBUTING.md).

Small first PRs are welcome and are the fastest way to learn the codebase's conventions. So is an issue that just says "this API is worse than the one I'm used to, here's why" — that is useful work.
