# Roadmap

Where frus is, where it's going, and — the point of this document — **what is unclaimed and ready for you to pick up**.

Items are tagged:

- 🟢 **An application had one theme where the reference's has four — done, milestone 452.** The reference wires most of an application's configuration on its app widget and reaches it anywhere through the build context; there is no context here, so it is reached through `self` — and `Application` already carried `theme`, `title`, `density`, `accessibility`, `scroll_physics`, `scrollbars` and `localizations`, with `MediaQuery::of()` and `localizations::of()` for the *reachable anywhere* half. What it did **not** carry was the second theme. The platform's brightness has been reported since milestone 380 and **nothing could act on it**, there being nothing to switch to. `dark_theme`, `theme_mode` (`ThemeMode::System` by default), the high-contrast pair, `theme_animation_duration` (200 ms) and `theme_animation_curve`; `resolved_theme` is the reference's `_themeBuilder` (`app.dart:995`) rung for rung, **on the trait** because without a context an off-screen renderer has to be able to ask `self`; and the **crossing** is the framework's, watching the *resolved* theme so a new palette fades exactly the way a light/dark switch does. The proof it was a real gap: this repo's own demonstration held `theme_from` and `theme_progress` in its state and interpolated in `theme()` — the reference's `AnimatedTheme` done by hand, and it lost all of it. Every default is what happened before, so nothing already written changes behaviour.
- 🟢 **An application had to write out its own reds — done, milestone 472.** `Colors`: the material palette as **308 plain `Color` constants** and 35 ramps. The reference's `Colors.red` is a swatch object that also happens to be a colour, because its language lets a class extend `Color`; Rust does not, and the naive translation would have made every widget signature in the framework generic over `Into<Color>` to buy the sugar back. So a tone is a `Color` and a **ramp is a separate type** (`MaterialColor::RED`, with `shade`, `steps`), because a ramp answers a different question — what a theme derives from, where a tone is what a caller picks. The steps are a slice and not a fixed array, so grey can state that it has twelve and the accents four, and `shade` can answer *nothing* for a step a family does not have rather than the nearest neighbour. The neutrals ship as **alphas** (`Colors::BLACK54` is black at 54 %), which is the whole point of naming them here: this framework has been bitten by a translucent token modelled as an sRGB blend, and the palette's own opacities are now somewhere to read rather than something to re-derive.
- 🟢 **Sixteen hand-drawn icons became 2 233 — done, milestone 472.** The old `Icons` was an enum whose every arm returned a hand-placed `Path`. Sixteen of them, each one good, and an approach that does not survive contact with a real icon set: nobody places two thousand icons by hand, and an enum closed at the crate boundary leaves an application whose mark is not in the set with **no way in at all**. So an icon is a value now — `IconData`, holding either an index into the bundled set or a `const fn` that draws a path, which is the escape hatch. `Icons` survives as the **name**: a unit struct of 2 233 associated constants, plus `by_name` for a name that arrives at run time and `all()` for a picker. The outlines live in a **307 KiB blob** rather than a megabyte of Rust nobody wants to parse every build, in seven byte-code opcodes at the font's own integer coordinates, with the blob's signature and offset table asserted at **compile time** — a stale or foreign file would otherwise decode into nonsense silently, in every icon on the screen. The grid comes from the blob too, so the grid the paths were generated on and the grid three widgets scale from cannot drift apart. **76 icons turn round for a right-to-left reading order** and the rest do not, from the set's own list, which is the half of that problem worth getting right. Thirty-four goldens carry the set's artwork now and were each looked at; nothing but the icons moved. Two more had been re-blessed and should not have been — `overflow_band` and `filters_three` hold no icon between them. Restored, and then chased properly in milestone 473, where it turned out the committed bytes were never what this machine renders and had not been since the day they were written. A picture that changes in a milestone that cannot have changed it is the cheapest bug in the suite to find and the easiest to bless straight past.
- 🟢 **One navigation, whichever chrome the width called for — done, milestone 473 (#47).** `NavigationDestination` is a **value** now, not a `(glyph, label)` pair repeated at each of the three chromes an adaptive application feeds. The type already existed inside the crate, already carried a selected icon and a badge, and was already what `NavScaffold` forwarded — behind `pub(crate)`. The work was deciding it was the caller's. `BottomBar`, `NavigationRail`, `NavigationDrawer`, `NavScaffold` and `Scaffold` all take `destinations`, and the positional builders are untouched: `item("★", "Home")` compiles as it did. A destination's mark is an `IconData` **or** a glyph (`DestinationIcon`, with `From` for both), which is what milestone 472 was for — an outline at rest and its solid twin when selected is the accessible way to say *this one*, where colour alone says nothing to a reader who cannot tell two colours apart. Tooltips too, by wrapping the item in the widget that already shows hints rather than writing a second one inside it. The two goldens milestone 472 left red were run down as well: both fail identically at the commit that first wrote them, and both render byte-for-byte today what they rendered 128 commits ago, so the difference is the **adapter's** and not the framework's. Each now states the tolerance it measurably needs — four pixels of one rounded corner, three counts of 255 on a blur's edge — and each was checked against a deliberate half-pixel of blur and one pixel of box width, which move 2 410 and 1 213 pixels. **The golden suite is 92 green**, and so is the one preview that lives outside it: `multiline_scrolled` had been red for months for a third reason again — its picture holds a scrollbar track this framework deliberately stopped painting and a thumb of the geometry it stopped using. Stale, not broken, and re-blessed; its test now wakes the bar's fade, because a bar that nobody has scrolled is correctly not drawn and a preview of a scrolled field needs one to be a preview of anything.
- 🟢 **The icon set's other three styles — done, milestone 472.** Outlined, rounded and sharp, one blob each behind `icons-outlined`, `icons-rounded` and `icons-sharp`, none on by default: 1.3 MB of artwork is not something to hand every application, and a feature that is off costs nothing at all — `include_bytes!` never runs and that style's constants do not exist. Nor does its *name*: `by_name` answers **nothing** for `"add_outlined"` without the feature rather than handing back the filled drawing, because an application that asked for one set and silently got another would ship looking wrong. The pairing is what the styles are for — an outlined icon at rest and its filled twin when selected is how a navigation bar says which destination you are on.
- 🟢 **Two icons recovered and one renamed — milestone 472, found by doing the styles.** The names had been read out of the reference's bindings by stripping a `_outlined` / `_rounded` / `_sharp` suffix, and two icons are *named* that way without being variants of anything: `insert_chart_outlined` and `wifi_tethering_error_rounded` are filled icons in their own right. Both had been silently dropped, and `class` had come through as `CLASS_`, carrying an escape belonging to the reference's language and not to the icon. Membership and codepoints now come from the **font's own manifest**, which states each icon and style explicitly and cannot be misread; the bindings are consulted only for the fifty-seven names that begin with a digit and therefore cannot be identifiers. An inference that is right two thousand times and wrong twice is the kind that ships.
- 🟢 **Icons turn round for a right-to-left reading order — milestone 472.** The sixteen places that painted an icon each wrote `path().scaled(size / GRID).translated(x, y)` by hand, and three carried their own copy of the grid constant to do it with. All sixteen go through `IconData::placed(size, x, y, direction)` now, which reflects in the vertical centre line of the square it just placed the icon in — so a mirrored icon occupies exactly the box an unmirrored one would, and no layout has to know it happened. Sixteen places to remember a rule in is sixteen places to forget it in. Not one existing golden moved, which is the evidence that `placed` is the expression each of them was writing.
- 🟢 **Three buttons touching had six lines where they should have four — done, milestone 471.** `ToggleButtons` (`toggle_buttons.dart:201`): a bank of buttons that share their edges, of which any number can be on. A row of outlined buttons pushed together draws every join twice, which is the tell that says *three controls* rather than *one control with three parts*; here each button draws only the edge facing the button before it, and only the last one draws the far end. **A seam belongs to the two buttons either side of it**, so either being on colours it (`:596`) — the rule a row of separate buttons cannot express at all, since there the line is drawn twice in two colours and paint order decides. Corners survive because every button but the last **grows its outline one hairline past the seam**, putting its far edge exactly where the neighbour's leading border will land: one rounded-rect call per button, one hairline per seam, and nobody owning an edge that is not theirs. The colour reaches the children through a `Themed` rather than through inheritance the framework does not have — a plain `Text` in a button takes the selected colour without being told, and one coloured by its caller still wins. Not `SegmentedButton`: that is one control with one answer, this is three answers. With `ToggleButtonsTheme`, `ToggleAxis`, vertical banks in both directions, and the golden that shows four lines and not six.
- 🟢 **A caption that took room out of the picture — done, milestone 471.** `GridTile` (`grid_tile.dart:22`) and `GridTileBar` (`grid_tile_bar.dart:25`): the strip of words goes **over** the picture, not under it, so the tile is the picture's size and a grid's rows stay even. The header and the footer are positioned layers and the child is not, which is what makes the child and only the child decide the box; a tile with neither is simply its child, and that is the reference's early return (`:45`) rather than an optimisation — a stack answers the walk's structural questions differently, and one claiming to be a stack over a single child would lay that child out loose. **The bar reads light whatever the application is**, because it stands on a photograph and a photograph has no brightness the theme knows about (`grid_tile_bar.dart:75`): a dark scheme for its own subtree, keeping everything that is not a colour — the typographic scale, the reading direction, the spacing, the application's widget defaults — where the reference's `ThemeData.dark()` throws all of that away too. Two heights the content picks between (68 with a subtitle, 48 without), a subtitle alone taking the title's type because it is the only line and not a second one (`:115`), and captions that cut rather than wrap. With `GridTileBarTheme` and a `foreground_color` the reference hardcodes.
- 🟡 **The crate names five axes for one idea.** `Axis`, `ReorderAxis`, `IntrinsicAxis`, `DismissAxis` and now `ToggleAxis`, because the shared one carries a `Both` that only a scrollable can mean and that nothing can be laid out along. The fix is one two-variant `Axis` plus a scrollable's own `ScrollAxis`, and it touches every call site of the five.
- 🟢 **The other half of the search bar — done, milestone 470.** `SearchAnchor` (`search_anchor.dart:121`): press the bar and a surface grows out of it holding the same query, a rule, and whatever the application thinks you meant. The reference pushes a `PopupRoute` and keeps `isOpen` in a controller because a Flutter widget owns its state; nothing here does, so the model holds `open` and the widget draws what the model says — which also deletes the controller, the application already having the string. **A full-screen view has no corners to round**: it is the screen, and a rounded screen is a rounded rectangle with the wallpaper showing through (`:1947`). Its header is 72 where a floating one is 56, and the sixteen is a thumb. The header is the bar again with three things turned off, the third of which was not a builder: **a bar with no surface has no state layer**, because a state layer is a lerp *from the ground* and a transparent ground lerped toward `on_surface` is a grey wash over whatever is behind the bar. With `SearchViewTheme`, `Localizations::clear_button_label` (not `close_button_label` — the same glyph means two things depending on what it sits in), and `OverlayPortal::new_boxed` for a widget that assembles its own anchor.
- 🟢 **A view with a header, a rule, and a blank — found and fixed, milestone 470.** The search view's suggestions live in a `SingleChildScrollView`, and one with nothing to grow into collapses to nothing and clips everything in it. The view has a floor of 240 its content does not reach, so **two** flex factors are needed and not one: the column fills the view and the list fills the column, which is exactly the reference's `Flexible(fit: tight)` inside a `Column` inside the view's constraints (`:1189`). Nothing in the tree was wrong — every widget present, every style resolved — and the picture was a blank rectangle. Third milestone running where the golden found what the tree could not.
- 🟢 **A field with no container, inside a container — done, milestone 469.** `SearchBar` (`search_anchor.dart:1404`): the raised pill an application searches from, which is not a form field with a stadium radius. A form field is sunk into the page, has a container of its own and floats a label into its border; a search bar goes **over** the content it filters, is raised, has no label, and holds a row of which the words are only the middle. Five lines of the reference's exist to say *this field has no container* (`InputBorder.none`), and there was no way to say it here — so `TextFieldVariant::None` and `TextField::borderless()` are new, and are what an inline table editor and a chip's input will want next. The hint's type resolves on **five** rungs rather than three, the two in the middle being the caller's and the theme's *value* style (`:1727`): a bar told to say its value in one type must not say its hint in another, and the field is empty exactly when the hint is the only thing showing. Its padding is applied **twice** (`:1783`, `:1790`), so eight from the edge to an icon and sixteen from that icon to the first letter. And a disabled bar **fades** where every other control here flattens: a raised pill has nothing to flatten to, its unavailability is the raising going away, and the exception is written down beside the constant. With `SearchBarTheme` (twelve fields) and the golden that shows the pill's corners are the pill's.
- 🟡 **A field's hint cannot have its own type step**, only its own colour. `TextField` draws its placeholder at the value's size, so `SearchBar::hint_style` carries a colour and not a size, and milestone 469's five-rung resolution is doing less than it says on one axis. The reference's hint is a full `TextStyle` (`search_anchor.dart:1560`). The fix is a second measured run in the field's own layout.
- 🟡 **A field cannot ask for the keyboard when it appears.** The reference's `autofocus` has no equivalent, so `SearchBar` has **no** `auto_focus` builder rather than one that quietly does nothing — which is the right call and still a gap. It needs the runtime to be told which widget wants the focus on the first frame it exists.
- 🟢 **The top of the panel, a rule that goes the other way, and a gap that is not a guess — done, milestone 468.** `DrawerHeader` and `UserAccountsDrawerHeader` (`drawer_header.dart`, `user_accounts_drawer_header.dart`) fill the header slot 467 opened and left empty; `VerticalDivider` (`divider.dart:244`) and `Spacer` (`spacer.dart:41`) are two things the framework had gone 467 milestones without. A header puts the top intrusion on its **height and its padding** — both, or the block below the notch is the wrong size. Its rule is its own **last pixel**, which is what the reference's `160.0 + 1.0` says. An account header anchors the **bottom** line on the control beside it rather than centring the pair, so that an address with no name above it lands in the same place (`:262`), and its arrow defaults to `on_primary` rather than the reference's white, which is right for a dark primary and wrong for a light one. `signed_in_label`, `show_accounts_label` and `hide_accounts_label` join the table — two for the control, not one that flips, because a control is named for what pressing it *will do*. A vertical rule **stretches on its own say-so**: a row that centres its children would hand it the height of its content, and its content is nothing.
- 🟢 **A row whose height had to be predicted twice — answered, milestone 468.** The account header's details row is 56 tall or as tall as its lines, whichever is more. Computing that overflowed by **0.600 pixels** from the type scale's `line_height`, and by the same 0.600 from a measurement of the strings: the laid-out box is a third number. A zero-width child of the right height floors the row and flexbox does the `max`. Two arithmetics that have to agree are one arithmetic too many — and this is the second milestone running where a constant from the reference could not be copied as a constant (467's indicator width was a ceiling; this is a floor).
- 🟡 **A box cannot tell its child how big to be.** The reference sizes an account header's pictures with `SizedBox.fromSize`, which passes **tight** constraints down, so a `CircleAvatar` under one is 72 across whatever it thinks. Here every widget sizes itself from its own `style()` and a parent cannot overrule it: `SizedBox` and `ConstrainedBox` set their *own* box, and a child that declares a length keeps it. So `UserAccountsDrawerHeader::current_picture_size` reserves the corner's room and the picture arrives at whatever size it was built with, which is a real difference and not a naming one. The fix is a way for a parent to hand a child a tight constraint — either a wrapper that overrides the child's declared size on both axes, or the walk passing constraints down the way the reference's does.
- 🟢 **The third navigation form, and the two that nobody could hear — done, milestone 467.** `NavigationDrawer` (`navigation_drawer.dart`): Material has three presentations of the primary navigation and this had two, so an application with more than five or six destinations had nowhere to put them. It is the **content** of a `Drawer` rather than a second panel, the shell here already being the thing that slides, scrims and docks. Its children are one mixed list, because **a destination's index counts destinations** (`navigation_drawer.dart:180`) and a divider that took a number would make every destination below it answer with the wrong screen while looking perfect. The indicator's declared `336` is a **ceiling**, not a width: the reference asks for it inside a 304-wide panel and gets 280, so a number lifted out of it carries the constraint system it was written under. And the glyph and the label take the **same** colour when selected, where a rail's do not — the pill is the whole row here, so the label stands on it. With `NavDrawerTheme`, a `NavScaffold::nav_drawer` band (opt-in: the reference gives two answers for the widest window and both are right), and the golden that shows all of it.
- 🟢 **A rail and a bar that announced nothing — done, milestone 467.** Reading the drawer's semantics turned up that `NavItem`, the row **both** the rail and the bottom bar are made of, had no `semantics()` at all. The primary navigation of every application built on this framework said nothing to a screen reader: not the name, not which one was live, not how many there were. Every visible part of it was right, every test was green, and no picture could have shown it. It now says the name and where it sits (`navigation_rail.dart:533`), with the label announced **whether or not it is drawn** — `RailLabels::None` is a decision about width, and a reader has no width. `Localizations::tab_label` joins the table, the first entry there that takes arguments.
- 🟡 **The crate's disabled guard is checking spelling.** `every_control_with_an_enabled_flag_honours_all_four` (milestone 322) reads the **source** of every module and looks for the literal `enabled: bool,`, then for the four hooks consulting it. Two milestones running have found it looking the wrong way: 465's control tiles folded their hooks into a `macro_rules!` body its rule for the end of a function cannot parse, and 467 established that the whole navigation family spells the flag `disabled` — `Destination`, `NavItem`, `DrawerTile` — so none of the three has ever been in scope at all. Both are one finding: a check that reads text checks how the text was written. The fix is to read the **expansion** and to match on the *contract* rather than on one spelling of it, which means a different tool than `read_to_string`.
- 🟢 **Four buttons whose meaning is fixed and whose name is not — done, milestone 466.** `BackButton`, `CloseButton`, `DrawerButton`, `EndDrawerButton` (`action_buttons.dart`): an icon button that already knows its glyph and takes its name from the framework's own words. None existed. What did was `IconButton::glyph("←")` at one call site — **a codepoint**, rendering in whatever the loaded font has for it, at the font's weight and on a text baseline, so beside a drawn 24-grid glyph it is the wrong weight and slightly the wrong height and no `icon_size` fixes either. It is also the same arrow everywhere, where the reference picks by platform (`action_buttons.dart:132`), and it was named by hand in the one place somebody remembered — the scaffold has a drawer and no button that opens it by name, a dialog has a cross and nothing that says "Close" to a reader. `Icons::ArrowLeft` is new, a head and a bar as two overlapping subpaths the way `cross_x` is two diagonals. Each button puts its label in **both** places, the semantics and a `Tooltip` — the first thing in the crate to use milestone 462's tooltip and 449's localizations together, which is what they were both for. `open_drawer_label` joins the table, **one word for both edges** as the reference has it, with a test whose only job is to hold that because it looks like an oversight. And `ActionIconTheme`, so an application with its own icon set does not leave four of the framework's showing through.
- 🟡 **A `macro_rules!` hides a widget from the crate's own guard.** `every_control_with_an_enabled_flag_honours_all_four` (milestone 322) reads the **source** of every module carrying an `enabled` flag and checks that `on_click`, `ink`, `focusable` and `semantics` each consult it. A hook written inside a macro body is text its rule for finding the end of a function cannot parse, so a module that folds its repetition into a macro leaves the net. It has now happened twice in two milestones — 465's control tiles and 466's action buttons — and both times the answer was to type the impls out. That is the right answer for two families and the wrong one for ten. The fix is for the guard to read the **expansion** rather than the text, which means a different tool than `read_to_string`.
- 🟢 **A row whose whole width works one control — done, milestone 465.** `CheckboxListTile`, `RadioListTile` and `SwitchListTile`, three of the reference's widgets and none of them here. Every part already was: `ListTile` takes two slots and a tap, and the three controls exist. What was missing is the thing that says *this row and this control are one control* — and that is not a convenience. **A settings screen where only the twenty-pixel box answers, and the label beside it does nothing, is a screen where most of the taps go nowhere**, and the person tapping does not conclude they missed, they conclude the application is broken. `RadioListTile` needed a radio and there was none: `RadioOption` was **private**, built by `RadioGroup` for each of its labels and unreachable from anywhere else, where the reference's `Radio` is a widget in its own right. It is public now, with its own builders, and the group still builds it from inside the module. The three share a private `Row` and a `row_builders!` macro and differ only in their control; `control_affinity` is trailing by default as the reference's is, and `secondary` takes whichever slot the control did not. Two decisions worth the words: the control answers with the **row's** message, ignoring the value it computed, because the application holds the choice; and disabled, neither answers, with two guards where it takes removing **both** to change the behaviour — which is what the test actually holds, said plainly rather than claimed as a proof of each. A new golden with all three in it.
- 🟢 **A floating action button was a helper that returned a button — done, milestone 464.** There was no `FloatingActionButton` here. There was `fab_button`: five lines returning a filled [`Button`], and it was the scaffold's entire answer for the most prominent control on a screen. **The colours were two roles out** — `Variant::Filled` is `primary` on `on_primary`, where the reference's takes `primary_container` on `on_primary_container` (`floating_action_button.dart:809`), which is the whole visual idea of an M3 floating button. There was **one size** where the reference has four, each carrying its own box, corner and glyph (40/12/24, 56/16/24, 96/28/36, extended); **no extended form at all**, so no way to write "New list" beside a plus; and it was a **circle**, `stadium()` taking half the short side where the reference rounds to sixteen. The widget now exists with `new(icon)`, `glyph(text)`, `extended(label)`, `.small()`, `.large()` and ten properties `FabTheme` mirrors, and `fab_button` survives as a **two-line shorthand for it** — its two callers in the demonstration are unchanged and both now get the right colours. Elevation six at rest, eight under a pointer, and **zero when disabled**: a control still floating while refusing to be pressed is telling two stories at once. A new golden shows all four sizes, which is the only way to see that each one's three numbers are three and not one.
- 🟡 **A docked floating action button has to be told it is round.** The reference's corner is sixteen, and a 56-pixel square rounded to sixteen leaves four corners hanging over the circular notch a `BottomAppBar` cuts for it — so `fab_button`, which is what the docked examples use, asks for a stadium explicitly. `Scaffold` cannot pick for the caller because it cuts the notch from the button's **bounds** and never sees its shape. Either the scaffold learns to ask (a method on the button, read where the notch is cut), or a docked placement overrides the shape on the caller's behalf and says so. The first is honest and the second is shorter.
- 🟢 **An expansion tile could not be themed, and had no shape — done, milestone 463.** `ExpansionTile` already had nine builders named after the reference's and resolved in the right order; what it had nowhere was a place to say any of them **once**. The exact gap `ListTile` had until milestone 458, on the widget usually built *out of* list tiles — a settings screen is a column of these, so an application that wanted its open sections tinted said so on each of them, and the tenth section written next quarter says it again or does not match. `ExpansionTileTheme` has ten entries, every colour in a pair, because an expansion tile is two things: the row that is always there and the row while what it hides is showing. It also had **no shape at all** where the reference's theme has two, and could take one for free since the row is a `ListTile` and a list tile has taken a shape since 457. The two stay apart: a tile naming only the open shape does not get it when shut, which looks like an omission and is a decision — square-when-shut, rounded-when-open is a design, and a fallback would make it unsayable, the same reasoning as the drawer's `end_shape` in 456. And `children_padding` was a **bare `Insets` with a value baked into the constructor**, so *nothing was said* and *zero on every side* were the same value: a theme rung under it could never have fired, and `children_padding(Insets::ZERO)` was indistinguishable from silence. Milestone 407's trap, three hundred milestones later, in a widget — a default written into a constructor is a decision nothing downstream can reverse.
- 🟢 **The place a tooltip goes, and no tooltip — done, milestone 462.** `Placement::Tooltip` has been in the overlay system since it was built: it puts a bubble above its anchor, **flips it below** when there is no room above, nudges it inside a window edge, and shows it **only while the anchor is hovered**. A whole small behaviour, written, documented and reachable from **nothing** — a search for `Placement::Tooltip` outside `ui.rs` and `portal.rs` returned no lines at all. `Tooltip` is not decorative: it is what makes an icon button legible, and a row of five unlabelled icons is a guessing game for a sighted reader and silence for a screen reader. The bubble is `inverse_surface`, the role the scheme has had all along, where the reference builds the same thing by hand out of white and grey in a `switch` on brightness (`tooltip.dart:481`). An **empty message is not an error** — it becomes the child and no overlay, so a caller with an optional hint need not branch — and the wrapper forwards its child's layout, milestone 425's rule. `TooltipTheme` has eight entries, because a tooltip is the one widget an application puts on *every* icon it draws. **A new golden**, in `motion.rs` beside the half-done swipe: a tooltip's picture is a fact about the `Runtime`, not about its arguments.
- 🟡 **A tooltip cannot be told to wait.** The reference's `waitDuration`, `showDuration`, `exitDuration` and `triggerMode` are all about **time**: how long a pointer must rest before the bubble appears, how long it stays, and whether a long press brings it up on a touch screen. The overlay system's gate is one equality against the hovered id (`ui.rs:3782`) with nowhere to put a clock, so a tooltip here appears at once and leaves at once. The way through is a per-overlay timer in the `Runtime`, which is also what `verticalOffset` and `preferBelow` need: both are constants in the placement arithmetic, and reaching them from a widget means carrying a number through the overlay pipeline that only one placement would read.
- 🟡 **`SemanticsProperties` has no `tooltip` field.** Milestone 462's tooltip puts its message in as a **label**, which `over` joins to the child's on its own line — a reader hears both, which is right, but it is not what the platforms expect. Both have a field for this specifically: `AccessibilityNodeInfo.setTooltipText` on Android and `AXHelp` on macOS, and the reference carries it as its own property. Adding it is a field, a rung in `over`, and a line in the platform bridge — small, and in `frus-shell` rather than in a widget, which is why it was not done in passing.
- 🟢 **A progress indicator was drawn to no specification — done, milestone 461.** Between them the two indicators had **two** builders, a width and a size; everything else was decided inside `paint` where nothing could reach it, and neither read a theme because there was none. The bar had two numbers nobody had chosen: a height of **eight**, twice the reference's four (`progress_indicator.dart:1624`), which reads as a slab rather than a line; and a track of `muted` faded to **thirty percent**, which is a colour arrived at by multiplying rather than one a designer picked — you cannot say "make the track quieter" about an expression. The reference gives it the `secondary_container` role. The look it takes is the reference's **current** one rather than its default one: the reference still defaults to a 2023 appearance behind a `year2023` flag it has already deprecated, saying it will default to the newer look in time, so a framework with no installed base to keep faith with starts where that one is going — a **gap** between the fill and the track, and a **dot** at the far end saying where the bar is headed, both builders so the older look can be written back. The ring stays a ring of dots rather than becoming the reference's arc (`paint_activity_ring` is shared with pull-to-refresh and the two must not drift into looking like different frameworks' idea of "busy"), and gained the three rungs it had none of: `color`, `stroke_width` and `track_color`. **One golden moved**, the only one with a bar in it. Two French comments went with it.
- 🟡 **An absolute in the reference keeps meeting a proportional rule here.** The menu's corner (four) met `theme.radius` in milestone 460; the ring's stroke (four, whatever the indicator's size) met `side * 0.12` in 461. Both times the proportional rule won and the reference's number was left reachable as an override, and both times the argument was made from scratch. It is the same argument, it will come up again, and it deserves writing down **once** as a rule this framework follows — probably next to the per-component corner question, which is the same shape.
- 🟢 **A menu was a stack of buttons, not a panel — done, milestone 460.** This was filed as mechanical, with a footnote that the menu "draws per-item rects, not one panel". The footnote was the milestone: `rebuild` handed the overlay a bare column of rows and each row painted its own filled, outlined, rounded rectangle, so an open menu was three buttons stacked with two pixels of the page showing between them. Adding a `shape` to that would have rounded the corners of something that was not a menu. A menu is **one surface**, off the page, with rows inside it (`popup_menu.dart:1837`): a `Panel` widget that did not exist, `surface_container`, a shadow at elevation 3, eight pixels of room above and below the rows, and rows that paint **nothing** at rest and light up under a pointer. Three numbers came with it, all the reference's: a row is a **tap target** and not 38 pixels (`popup_menu.dart:279` — ten under what the accessibility scanners on both mobile platforms check for, on a widget whose entire purpose is to be tapped), the label is `labelLarge` and not `titleMedium`, and the row's twelve pixels of padding is now a named number rather than one hard-coded at the call site. `MenuTheme` went from one field to eight and the button gained seven builders. **One golden moved**, and it is the point of the milestone.
- 🟡 **Every component has the same corner.** The reference gives each one its own — four for a menu, twelve for a card, sixteen for a dialog, twenty-eight for a sheet — where this collapses them all into a single `theme.radius` an application sets once. The collapse is defensible and it is why milestone 460 did not give the menu the reference's four: doing it for one widget makes that widget the only thing on screen ignoring the number the application set. Doing it for **all** of them is the real change, and it is a per-widget default in `WidgetThemes` plus every golden with a corner in it. Worth deciding once, deliberately, rather than one widget at a time.
- 🟢 **Twelve colours that promise not to move — done, milestone 459.** The `*Fixed` set: `primary_fixed`, `primary_fixed_dim`, `on_primary_fixed`, `on_primary_fixed_variant` and the secondary and tertiary equivalents (`color_scheme.dart:90`). Every other accent role is answered twice, once per brightness; these are answered **once**, and both themes give the same answer. The requirement is ordinary and this framework could not express it: a card carrying a brand colour, an onboarding page whose illustration was drawn against one particular green, a header signed off in a design review against a paper swatch — all of them want a container's *emphasis* and cannot accept a container's *behaviour*. This entry used to say they have no relationship to the rest of the scheme a test could hold them to, and **that was wrong**: they are tones 90, 80, 10 and 30 of the accent's own palette, which makes them both derivable and testable. The written pair is read off this crate's own HCT and put **byte for byte identically** into `dark()` and `light()`; `from_seed` writes the same four tone calls in both branches, so there the promise holds by construction. Two tests: one walks all twelve across the written pair and three seeds, the other holds the ordering and the legibility — including the constraint that makes the set interesting, that there is **one** `on_*_fixed` and **two** surfaces it has to be readable on, since a caller reaching for the dim one for emphasis does not get to re-pick its text colour. The six fixed pairs joined the existing `from_seed` contrast sweep. Nothing paints them yet, which is correct — the reference leaves them for makers too. **Breaking**: `ColorScheme` has twelve more fields.
- 🟢 **A list tile's theme, and a sheet that takes a shape — done, milestone 458.** `ListTileThemeData` is one of the reference's larger tables and there was **no `ListTileTheme` here at all**, so every property a tile has was the caller's alone — and a list tile is the most repeated widget in most applications, a settings screen being thirty of them. Thirteen entries on the usual rungs. `height()` had no theme in hand and is public, so it now delegates to `height_for(theme)` the way `style()` already delegates to `style_themed` one screen up in the same file: the file's own idiom beat inventing a second one. And the bottom sheet's corner was `theme.radius + 6.0` — sixteen pixels arrived at by adding six to something else, unreachable by caller or theme; `BottomSheet::shape()` and `BottomSheetTheme::shape`/`radius` resolve it now, with the framework's own default left **exactly** where it was. The test also found a sharp edge worth naming: `BottomSheet::body` is what wraps the panel, so `open().shape(..)` compiles, runs and does nothing — `background` has always had the same trap and nothing said so.
- 🟡 **A bottom sheet's default corner is still not the reference's.** Material 3 puts the top pair at 28 and this rounds them by `theme.radius + 6.0`, which is 16. The number is reachable since milestone 458; changing the **default** moves every picture with a sheet in it, so it wants doing with the goldens read rather than in passing.
- 🟡 **A sheet's style is read when its body is wrapped, not when it is built.** So `BottomSheet::background` and `shape` are silently ignored if they are called after `body`. A builder whose method order matters and does not say so is a bug waiting for somebody's afternoon; the fix is the panel reading its style at build time.
- 🟢 **Properties a list tile and a divider did not have — done, milestone 457.** A batch rather than a theme, and the pick of it is `selectedTileColor`: this had `selected_color`, the colour of the **words**, and nothing else — so being *the one you are on* changed the text and nothing about the row, which in a list of ten is close to invisible. It now outranks `tile_color` while selected and says nothing otherwise, as the reference's does; `icon_color` and `text_color` came with it. `ListTile::shape` follows, with the surface **and the ink** taking it — `InkStyle::radius` existed for exactly this and nothing had ever set it from a tile, so a rounded tile would have splashed square corners for the length of every tap. And `Divider::radius` (`divider.dart:68`): a hairline keeps its square ends and the fast fill path, a thick rule reads as a bar, and a bar with square ends is about the only thing left in an interface that still has them. The goldens did not move.
- 🟢 **A radius that follows the reading direction — done, milestone 456.** A `BorderRadius` says *top left*, which is a statement about the **wall**; an interface that mirrors needs to ask which corner is at the *beginning of the line*. For most things the two coincide and nobody notices; for anything asymmetric they part company. A drawer rounds its **inner** edge — the *end* side for a leading panel, which is the right in English and the left in Arabic — and this framework had no way to say that, so the panel folded the side and the direction into one `docked_right` and picked `left` or `right` by hand. Correct arithmetic standing in for a word the framework did not have, exactly like the button's `height / 2` in milestone 451. `BorderRadiusDirectional` is `top_start`/`top_end`/`bottom_end`/`bottom_start` and one `resolve(direction)` — two plain types rather than the reference's `BorderRadiusGeometry` hierarchy, because a widget here is handed a `&Theme` and always has a direction in hand. `Drawer::shape()` follows, with `DrawerTheme::shape` **and** `end_shape` as two fields as the reference has them (`drawer.dart:268`), a trailing panel deliberately **not** falling back to a leading panel's shape. The goldens did not move.
- 🟢 **The shapes milestone 451 said it had done — done, milestone 455.** An audit of every `shape` property in the crate, and 451's own CHANGELOG turned out to be over-claiming. **`Card::shape()` did not exist**: the card got the field, the four-rung resolution and a test, and never a builder — a resolution with no way to reach it reads as finished from the inside, and every card test went through `radius`. **`SnackBar::shape()` did not either**, and its resolution was passing the theme's answer into the *caller's* slot with nothing in the theme's: correct only for as long as no caller existed. And **`AppBar` was not one of the six** — a property named `shape` typed as a `BorderRadius`, with a doc comment arguing the narrowing that was true until milestone 450 built `ShapeBorder` and expired the day it did; `AppBarTheme::shape` was the last theme field in the crate carrying the reference's word with a corner behind it. A bar is a rectangle, so a shape gives it the corners it **resolves to in the bar's own box**: `stadium()` is 32 on a 64-high bar and 40 on an 80-high one, with no arithmetic at the call site — which the radius-only property could not express at all, the same bug 451 fixed in `Button`. **Breaking**: `AppBar::shape` takes a `ShapeBorder`; a caller passing a number says `radius`.
- 🟢 **Two widgets still have no shape.** `DatePicker` and `TimePicker` have none at all where the reference does — though both live inside a `Dialog`, which has one, so the question is whether they should own a shape or take the dialog's. The sheet was done in milestone 458 and the menu in 460, where it turned out not to be mechanical at all.
- 🟡 **An app bar does not react to content scrolled under it.** The reference's `scrolledUnderElevation` (`app_bar.dart:205`) is an M3 signature: the bar takes on elevation and surface tint the moment the page moves beneath it. Milestone 447 already defined the state it is expressed as — `WidgetState::ScrolledUnder`, one of the reference's eight (`app_bar.dart:918`) — and **nothing sets it**. What is missing is the wire: the scroll offsets live in the `Runtime`, `ScaffoldInfo` is built from the `Scaffold`'s own fields with no runtime in reach, and `build_deferred` (the between-frames build) has no runtime at all. Getting that asymmetry wrong is milestone 408's bug, so it wants deciding before it is written.
- 🔴 **A style cannot say `letterSpacing`.** The reference's `TextStyle` has `letterSpacing`, `wordSpacing` and `fontFeatures`, and the **Material 3 type scale specifies letter spacing per role** — 0.1 on `labelLarge`, 0.4 on `bodySmall` — so every label in this framework is tighter than the reference's by a documented amount. It is blocked below us: cosmic-text 0.12.1 has no `letter_spacing` on `Attrs`, and `BufferLine::layout_opt()` hands back an immutable layout, so the shaped glyphs cannot be nudged after the fact either — and wrapping would have to account for the spacing anyway, which happens inside cosmic-text. The way through is a newer cosmic-text (and the matching glyphon), which is a dependency move worth planning.
- 🟢 **The device's language never reached the application — done, milestone 454.** Milestone 408's trap, twice over: `frus-l10n` has had Fluent and its negotiation for a long time, milestone 449 gave the framework a `Localizations` table — and **nothing ever told either what language the device is set to**. Every platform reports it; nothing here read it. So an application hard-coded a language or asked the reader to pick one on a device that already knew, and both halves passed every test they had, because a test picks the language it is testing. `Locale` is the reference's shape (a required language, an optional script and country), read by the **shape** of its subtags as BCP 47 does — so `zh-Hant` and `zh-TW` both parse without a table of every code — and `locale::resolve` is `basicLocaleListResolution` (`app.dart:146`) rung for rung, including the one worth understanding: a language-only match is **held back** from the reader's second choice onward, and their **first** choice is trusted instead, because asking for French first outranks an exact match on a language asked for second. The wire: `sys-locale` on the desktops and iOS (already in the tree — cosmic-text pulls it), `Configuration.getLocales()` over Android's existing JNI walk, `navigator.languages` on the Web. It also found an **ordering bug**: `install_ambient` sat beside the build, which is one frame late for the theme — and the direction of the layout follows the language. The demonstration lost its hard-coded language and now opens in the device's. Checked on three targets, and the Android one caught an error the desktop build could not see.
- 🟢 **A theme could not say whether it was light or dark — done, milestone 453.** The reference carries `brightness` on `ColorScheme` and on `ThemeData`; this carried it nowhere, and the one place that needed the answer worked it out: `surface.compute_luminance() < 0.5`, the scrollbar deciding how present its thumb is, where the reference reads `_colorScheme.brightness` (`scrollbar.dart:232`). The guess agrees with the declaration on all four schemes this crate builds — which is exactly why it survived every test — and stops agreeing the moment an application writes its own: a **dimmed light** scheme has a surface below the halfway line and is not dark, and the numbers either side are three times apart at rest. Luminance is a property of one colour; brightness is a property of a design. It does **not** interpolate — `lerp` takes the destination's, discretely, as it already does for the text direction. **Breaking**: `ColorScheme` has one more field.
- 🟡 **A status bar's icons do not follow the theme.** The line after the reference resolves a theme is `SystemChrome.setSystemUIOverlayStyle` (`app.dart:1012`); nothing here sets it, so a light theme on a device draws white icons on a white bar. Milestone 453 made the framework half writable — `Theme::brightness()` and `Brightness::inverted()` exist. The platform half is a **tooling** prerequisite, not a design question: setting the system bars' appearance on Android must happen on the Java UI thread, `android_main` is not it, and the way across already exists (`FrusTextBridge` uses `runOnUiThread`) — but adding a method to it means rebuilding `assets/frus_input.dex`, which needs a JDK and `d8` from the Android build-tools.
- 🔴 **The rest of what an app widget wires.** `shortcuts` and `actions` — an application-wide key map, which is also what an `Intent` needs — and `color`, the tint a task switcher paints an application's card with. `builder` is **deliberately not** on this list: its value in the reference comes from the app widget building the `Navigator` for you, `builder` being the only way to get above it, and here `view` builds the whole tree already. Porting it mechanically would add a hook with nothing to do.
- 🔴 **A localization table is not chosen by locale.** Milestone 454 resolves the language and installs it; an application still hands the framework **one** `Localizations` table rather than one per locale, so it has to read `locale::of()` and switch tables itself. The reference has a `LocalizationsDelegate` per locale and loads them asynchronously. The next entries the framework will need include ones that want **plurals**, which is where a table of strings stops being enough and the format has to be part of the entry.
- 🟢 **Six widgets that took a corner now take a shape — done, milestone 451.** `Card`, `Chip`, `Dialog`, `Button`, the FAB and the snack bar, together, because a property meaning one thing on a card and another on a button is worse than one that is missing. One rule, `resolve_shape`: the caller, then the theme's shape, then the theme's plain radius read as a rounded rectangle, then the widget's default. On the widget there is **one** field — `radius()` is a shorthand that writes a rounded rectangle into it and the last builder called wins. Two were **wrong**, not merely limited: a button's stadium was `height / 2`, right only for a button wider than it is tall (a 24×80 one asked for a 40-pixel corner on a 24-pixel box), and the FAB was the same number written out. And `DialogTheme::shape` carried the reference's *name* with a `BorderRadius` behind it — now a `ShapeBorder`, which is a **breaking change** for anything that passed it a number.
- 🔴 **`ContinuousRectangleBorder` is the fifth shape and does not fall out of arcs.** The reference's superellipse — its “squircle” — needs its own path, and it is what Material uses where a rounded rectangle looks subtly wrong at large radii.
- 🟢 **A box could not say what shape it was — done, milestone 450.** A box here had a `radius: f32`; the reference has a family, and `shape` is not decoration — it is what decides a chip is a stadium, a floating button a circle, and a rail's selection indicator a pill. `indicatorShape`, `Card.shape` and the rest were blocked since milestone 437 not because each was hard but because the type they all need did not exist. `ShapeBorder` has four — rounded rectangle, stadium, circle, bevel — with a `BorderSide` around any of them, and it is `Copy` so it can sit in a theme. **Three of the four are rounded rectangles once the box is known** (`stadium_border.dart:95`, `circle_border.dart:126`), so `as_rounded` hands back the box *and* the radii — two things, a circle not occupying the box it was given — and they cost the renderer nothing new; `outline` answers for all four as a path, which the bevel needs and shape-clipping will. First user: a destination's `indicator_shape` (`navigation_rail.dart:1148`), where the old line was `pill_h * 0.5` — a stadium's arithmetic written out at the call site, right but unable to be told anything else. **The goldens did not move**, which is the point.
- 🟢 **No widget could name itself in the reader's language — done, milestone 449.** A framework says a certain amount out loud on an application's behalf — the label on a back arrow, the word on a notification's cross, a calendar's month names — and every one was an English string constant, with the twelve months written out **three times**. It was not only untranslated: the calendar always started its week on **Sunday**, so across most of Europe every date in the month sat a column or two out of place. `Localizations` is a trait whose methods all have English bodies, so a table writes down only what differs; it reaches widgets through the ambient-scope idiom `MediaQuery` already uses, and **not** through the theme — what an interface says is a different question from what it looks like. `first_day_of_week_index` indexes a `narrow_weekdays` list that is **always Sunday-first** (`date.dart:353`), which is what lets one number serve as both the index and the rotation. The guard is `a_shell_installs_the_application_s_words`, driving the shell's own reading of the trait: `of()` answering English by default is what makes the feature safe to add **and** what would hide the wiring being missing — milestone 408's bug exactly.
- 🔴 **A localization table has seven entries where the reference has a hundred.** And no loading: the reference has a `LocalizationsDelegate` per locale, this has one trait and whatever an application hands it. The next entries the framework will need as it says more — a drawer's tooltip, a dialog's, the row-count phrases a table speaks — include ones that need **plurals**, which is where a table of strings stops being enough and the format has to be part of the entry.
- 🟢 **A theme is eight kilobytes, and it was `Copy` — done, milestone 448.** Milestone 447's property could reach widgets and not themes, which is where the reference keeps most of them. Removing `Copy` to fix that turned up something worth fixing anyway: `Theme` measures **7952 bytes** and `WidgetThemes` 5816, so every `*theme` in the crate was an eight-kilobyte `memcpy` that read like a pointer copy — nine of them, in the layout walk, in every themed subtree, once per overlay. None is in an inner loop, which is why nothing was ever slow enough to notice; but `Copy` on a struct this size makes the expensive thing invisible, and the next person to write `*theme` inside a loop gets no warning. The nine are now `clone()` calls that say what they cost. `NavRailTheme::overlay_color` is the first theme field that is a property rather than a value, resolved on the usual three rungs — and a property matching no entry **falls through** rather than answering with a default, which is what makes naming one state safe.
- 🔴 **The walk still copies a theme into every themed subtree.** Eight kilobytes per `Themed`, and again for the walk's own field. An `Arc<Theme>` would make it a refcount bump and `Themed` nearly free, but it changes the signature every widget's `paint` and `style_themed` is written against — a mechanical change across the whole crate, and one worth doing deliberately rather than in passing.
- 🟢 **A value that depends on what a widget is doing — done, milestone 447.** The reference threads one idea through every Material component: a property is not a value but a **function of the states the widget is in** (`widget_state.dart:821`). Nothing here could say that, and the notes have wanted it since milestone 322; what existed was `Theme::state_layer`, one lerp towards an ink at three fixed opacities — right for a state layer, no answer for a caller who wants a particular colour in a particular state. `WidgetState` is the reference's eight (`:168`); `WidgetStates` is a **byte** rather than a hash set, so it is `Copy` in a paint walk and can join the rebuild hash; `StateFilter` combines with `&`, `|` and `!`; `WidgetStateProperty` tries entries in order and the **first match wins** (`:1009`), so a narrow entry goes before a wide one. Two departures, both deliberate: **no closure form** (a map is `Clone`, `Debug` and comparable, which a tree rebuilt every frame needs), and **resolving to nothing is an answer** — naming one state does not silence the rest. `Status::states` answers for three of the eight, because three are all it honestly knows; selection, disablement and the rest are the widget's own to add. First user: a destination's `overlay_color` (`navigation_bar.dart:232`).
- 🟢 **A snack bar has one behaviour where the reference has two — done, milestone 446.** `SnackBarBehavior` (`snack_bar_theme.dart:27`) is a question about **position** — fixed to the bottom of the scaffold, pushing the other non-fixed things up; or floating above them, moving nothing — and everything else follows from it. A fixed bar has **no corner at all** (the reference passes a shape only when floating, `snack_bar.dart:798`), holds its text in by 24 rather than 16 (`:687`), and keeps nothing clear of the page; a floating one rounds at 4, pads by 16, and keeps `insetPadding` — 15, 5, 15, 10 (`:989`). The default is **fixed** (`:986`). This rounded every bar and padded every bar as though it were floating, which left four slivers of page showing through the corners of a bar that was flush against the edges. `width` and `margin` are floating's alone (`:678`); a fixed bar ignores both, a width being a contradiction rather than an override. And the inset moved **into the bar**, where the reference keeps it (`:823`): `ScaffoldMessenger` was imposing 16 on everything it held, which a floating bar then added its own margin to.
- 🔴 **A snack bar still sizes itself to its text.** The reference never does: a fixed bar spans the page, and a floating one spans the room it is given less its margin (`snack_bar.dart:734`). Spanning means stretching on the host's cross axis, and the fade wrapper in between shrink-wraps — `AnimatedOpacity` forwards its inner `Container`'s style, not its child's. Underneath it is a question about what a notification layer **is** here: the reference's messenger shows one bar across the bottom of the scaffold, and `ScaffoldMessenger` is a corner that stacks several.

## Near term

The things standing between frus and someone else being able to use it.

### Distribution

- 🟡 **Publish to crates.io.** Everything resolves through local `path` dependencies today. This needs real versions, per-crate `README`s, metadata (`repository`, `keywords`, `categories`, `documentation`), a publish order that respects the dependency graph, and a release script. Once done, the `cargo generate` template drops `{{frus_path}}` and becomes `frus = "0.1"`.
- 🟢 **Per-crate `README.md`.** Each crate needs a short one for its crates.io page.
- 🟢 **Pin an MSRV.** There is no `rust-version` in any manifest and no minimum supported Rust version has ever been tested. Find the oldest stable that builds the workspace, put `rust-version` in `[workspace.package]`, and add that toolchain to the CI matrix.
- 🟡 **docs.rs-quality rustdoc.** Crate-level docs with a runnable example on every public crate, and `#![warn(missing_docs)]` turned on crate by crate.

### Web parity

The web target renders and animates but is missing its platform integrations. Each of these is an independent, self-contained job.

- 🟡 **Clipboard** via the async Clipboard API, behind the same interface desktop uses.
- 🟡 **Accessibility.** AccessKit has web support; the semantics tree already exists and is populated. This is a bridging job, not a from-scratch one.
- 🟡 **IME / soft keyboard** on mobile browsers — a hidden input overlay, composition events, viewport insets.
- 🟡 **Live-reload** for the wasm target.
- 🟢 **A proper web example page** — the current `index.html` is minimal.

### Size

Milestone 292 took a release APK from 286 MB to 4.9 MB by building `--release` at all. What is left is real work, not settings.

- 🟡 **Subset the bundled faces at build time.** DejaVu covers far more of Unicode than any one application draws, and the four `bundled-*` features are a coarse instrument next to a `pyftsubset` step over the glyphs a build actually references. This is where the next megabyte is, and it needs a tool in the build.
- 🟢 **A size regression check in CI.** Nothing notices today if the floor doubles. Build `frus-hello` for `aarch64-linux-android` in release, compare the stripped `.so` against a committed budget, fail on a jump.
- 🟢 **Document `--split-per-abi`-style packaging.** The examples build `aarch64` only; an application targeting more than one ABI wants a split rather than a fat APK, and nothing says so.

### Quality

- 🟢 **Clear the clippy backlog — done, milestone 298.** 71 warnings, now zero, and CI runs `cargo clippy --workspace --all-targets -- -D warnings` as a **blocking** check. Six `too_many_arguments` carry a targeted `#[allow]` with the reason at the site; everything else was rewritten.
- 🟢 **Format the tree — done, milestone 298.** One `cargo fmt --all` commit over 40 files, on its own, and the fmt check is **blocking** now.
- 🟢 **Widen golden coverage — done, milestones 296 and 297.** 58 of the 86 widget modules had no pixel test at all; **all 86 have one now**. 296 added 27 goldens for the widgets whose picture follows from their arguments; 297 added `frus_test::Stage`, a harness that holds the retained state and steps the frame loop the way the shell does, and 12 more for the ones whose picture is a gesture in flight — a swipe half done, a pull past the top, a glow, a page between two pages.
- 🟢 **An overlay belongs to its screen — done, milestone 326.** The red item found on a device: an app bar's overflow menu, left open while choosing "Settings →", stayed drawn over the screen that replaced it. Neither obvious explanation was right — no retained state leaked, and the outgoing screen had not left the tree (during a transition it is genuinely still in it, and once the spring settles the menu goes with it). Reproducing it through `Application::view` and printing the item's position every frame showed the actual cause: it never moved. `process_overlays` runs after both screens and paints above the **whole window**, so a deferred overlay outranks the screen drawn on top of its owner; and the transition is parallaxed, so the outgoing screen travels only 30 % of the width and the anchor never leaves. Everything a container paints goes through `Widget::paint`, which the walk calls before it descends — right for a background, useless for the cases that exist: an outline over a photograph, a wash across a disabled tile, a hairline over a card, all of them decorations whose point is that the content does not cover them. Data rather than a second `paint`, because a general paint-over cannot be skipped cheaply — the walk has no way to know an empty body — and a decoration is what the feature means; `None` costs one `Option` check per node. It went in `walk_node`, the innermost of the four wrappers with no early return to leak past, which puts it inside the opacity group, transform and shape clip the container asked for, under its own theme override, and inside the repaint-boundary capture. Nothing from that audit is left on `Container`: `transform` was a false gap (the `Transform` widget has always existed) and `constraints` is `ConstrainedBox`.
- 🟢 **A reversed area glowed at the wrong end, and a rounded box did not confine its child — done, milestone 361.** Two notes left twice over. The glow and pull-to-refresh both read the sign of a refused delta in *offset* space and assumed offset zero was the top of the screen — which reversing is precisely the act of denying, so a conversation refused at its newest message lit up at its oldest. `Scrollable::refused_edge` states that assumption and corrects it in the one place both call sites share, and `Scrollable::start_edge` answers the different question the refresh guard was really asking: not "did this refusal happen at the top" but "which edge does this axis begin at". Separately, `Container::clip()`: the reference defaults `clipBehavior` to none because a decoration is painted behind a child and confining one costs a layer, but ours could not be asked at all, so a box with rounded corners always left a photograph inside it square. Its own radius is now available as the child’s clip, reusing the compositing path `ClipRRect` already drives. Left on `Container`: `foregroundDecoration`, a decoration painted *over* the child, which has no workaround short of a `Stack` and no hook either — nothing in the widget trait paints after its children, so it is a walk change and wants its own step.
- 🟢 **A list could not count from the bottom — done, milestone 360.** The other half of a conversation view: a scroll anchors its *content* to the end, but only a list decides which end an *index* is. `List::reverse()` puts item 0 at the bottom, so with index 0 the newest message, appending one leaves every other item exactly where it was — the view does not jump and nothing is renumbered. The virtualisation window needed no change: a reversed list counts indices from the end and a reversed scroll counts pixels from the end, so index and offset agree about which way forward is and only the item's landing place differs. That is what milestone 359's choice of offset origin bought; numbering from the top would have needed the window arithmetic mirrored in a second place, disagreeing with the first. Left: a reversed area still glows at the **top** for movement refused at what is now its start — `edge_for` reads the sign of a refused delta in offset space — the same class as the pull-to-refresh note in 359, wanting one fix for both.
- 🟢 **A scroll could not run from the far end — done, milestone 359.** Third of milestone 357's audit findings and the one with teeth: no `reverse`, so a conversation — the canonical use — could not be built. Two things it buys, neither cosmetic: content shorter than the viewport sits at the bottom, and the view **stays** at the end when content arrives. The second decides the design: offsets are measured from the end an axis starts at, so a view resting at offset 0 rests at the newest message wherever the end now is. Numbering from the top would leave it drifting away every time something was appended, which is the one thing this exists to prevent. The sign change lives in **one** function, `Scrollable::offset_delta`, called by all five places a screen delta becomes an offset — a minus sign at each would have been five chances to be wrong in a way only a device shows. Nothing changes for the user's hand. Left: `List` and the virtualised list do not reverse (a reversed list also has to *build* from the end, which is the item walk rather than the offsets — the other half of a chat view), and pull-to-refresh above a reversed area takes the top edge where its start is the bottom.
- 🟢 **An image had to be told its own size — done, milestone 358.** Second of milestone 357's audit findings: `Image::new(handle, width, height)` required both numbers, so a picture could not be shown by anyone who did not already know its pixel dimensions. Both are optional now and the reference's rule fills in the rest — both given is that box, one given derives the other from the image's ratio, neither is the bitmap's own size — which all falls out of the layout engine once the widget stops insisting. `alignment` covers both jobs one anchor has: where a letterboxed image sits in its box, and which part of a cropped one survives, running opposite ways (aligning to the top keeps the top of the box in one case and the top of the *image* in the other). `opacity` goes into the tint an image is already multiplied by rather than costing a layer. One caveat the tests caught and the docs now state: a **stretched** cross axis beats the ratio, which is the parent's say and the reference's behaviour too. Left: `repeat` (a sampler that wraps rather than clamps — the only item that reaches the GPU crate), `filterQuality`, and the loading/error builders, which wait on image loading being asynchronous.
- 🟢 **A stack could not place a layer — done, milestone 357.** The widget catalogue milestone 336 counted is closed, so what is left is **depth**: a widget's presence is not its every property. An audit of the reference's constructor parameters against our builder methods, for two dozen widgets applications actually reach for, is a pointer rather than a count — without a synonym map `textAlign` reads as missing when we spell it `align` — and where it pointed worst was `Stack`, whose entire surface was `new/width/height/flex/layer` against the reference's alignment, fit, and `Positioned`, which did not exist. `Positioned` pins any of the four edges, and what is pinned decides the layer's size as well as its place. The default `StackFit` stays `Expand` where the reference's is loose, deliberately: a loosely-constrained childless box fills in the reference and hugs here, and a scrim, a barrier and every internal overlay are exactly that widget. Three things the tests caught: a hook the wrapper macro did not forward, a pin that has to **overrule** a child's own size (`Layout::compute_tight`, the third answer next to asked and handed), and a one-layer stack that would have shifted twice through the single-child alignment path. Left, from the same audit: `Scroll` has no `padding` and no `reverse`; `Image` has no `width`/`height`/`alignment`/`repeat`; `Container` has no `transform`.
- 🟢 **A grid could not work its own column count out — done, milestone 356.** The reference's other grid delegate takes a maximum tile width and derives the count: `ceil(width / (max + spacing))`, at least one, the rest divided equally — four columns of 125 in a 500 px grid at `extent(150.0)`. CSS `auto-fill` looks like the same idea and is not: it fits tracks of **at least** the given extent, so it would give three of 166, one column out and in the direction that matters. The count therefore has to be computed from a width that does not exist until the layout has run, which is the wall milestone 353 stopped at and milestone 355 took down. The cells come from a factory, indexed like a list's rows, because there is no grid to put them in until the count is known; `Grid::new` is untouched and the two share every builder method. **Its first tests found a defect one widget along from milestone 351**: a `LayoutBuilder`'s content was *constrained* rather than *handed* its box, so a root with no width of its own hugged and a grid built there laid its columns out at nothing — the third time that distinction has come up, now fixed in the measurement and the paint. One golden moved and was read. Left: no column spans (the reference has none on this widget either), and a late-building grid is not layout-cached.
- 🟢 **A `LayoutBuilder` laid out 0 px tall — done, milestone 355.** The reference sizes it to its child (`size = constraints.constrain(child.size)`); ours was a layout leaf whose size came from its style, and its own module documentation admitted it under the heading *the sizing contract*, telling you to go and find a height. The way out was already in the framework: `measured_leaf` registers a closure the engine calls **during** the computation with the space actually available — how a paragraph is measured, and the same moment as `runLayoutCallback()`. The closure builds the subtree, lays it out in a tree of its own and returns its size. It cost a lifetime on `Layout` (`MeasureFn` was `'static`, and a measurement that calls back into the widget layer has to borrow the tree; the theme could not be borrowed at all, since a themed subtree's is a local, so it is copied) and a **hole in the relayout cache**: a closure has no fingerprint, two identical-looking frames can want different boxes, so a root holding one is recomputed every frame rather than risk a stale one — a cache that is right most of the time being worse than none. An axis the style pins is still the style's, so every existing use behaves identically and all 91 goldens are unchanged. Left: the responsive grid delegate from milestone 353, which this now makes writable.
- 🟢 **A grid's rows were as tall as whatever was in them — done, milestone 353.** The reference's grid delegate derives a main-axis extent for every tile from the track it just sized — `childAspectRatio` defaulting to 1.0, so tiles are square — and hands each child a box tight on both axes; ours let each row follow its content, so a board of tiles came out as ragged bands. `Grid::aspect(ratio)` and `Grid::tile_height(px)` now say which, and `row_gap`/`column_gap` split what was one `gap`, as the reference's two spacings are separate. The ratio is the *container's* say and cannot be asked of a tile — a tile does not know how wide its column came out — so it is imposed during the walk, the third thing resolved there next to the fill request and the shrink grant. The reference's default of square tiles is **not** taken: `Grid` is also the framework's plain CSS grid and four widgets are built on it. Checked in passing and already right: a **scroll** fills its content's constrained axis when exactly one is free, and a **table**'s cells are tight across and free down. Left: the reference's *other* delegate, which derives the column count from a maximum tile width — it needs the grid's computed width before the layout, which is `LayoutBuilder`'s job, and `LayoutBuilder`'s height does not follow its content.
- 🟢 **`Flexible` by name — done, milestone 354.** The loose fit had existed since milestone 334 as `Expanded::loose()`, tested in both directions; it simply was not called what the reference calls it, where `Flexible` is the widget and `Expanded` its `fit: FlexFit.tight` subclass. `Flexible` and `FlexFit` are here now with the reference's defaults on both — an `Expanded` is tight, a `Flexible` is loose — and they build the **same box**: the three properties that make a flex item (a basis, a grow factor, the lifted automatic minimum) live in one `flex_item` both wrappers call, because that box already cost three milestones once and a second copy is a second place for the next fix to miss. Left, unchanged: `shrink()` is still on `Flex` and `Container` only while ten other widgets carry `flex()`; **milestone 349 made that matter much less** by turning the default around — nothing is squeezed unless it says so, which is what those ten widgets wanted from `shrink(0.0)` in the first place.
- ✅ **`Text` could not be aligned, limited or faded — done, milestone 343.** `TextAlign`, `max_lines` and the reference's four `TextOverflow` modes, on the widget every screen is made of. Two things had to be true before any of them could work: an aligned text has to **fill** the box it is offered, because a box exactly as wide as its own words has nowhere to align them to; and a text that has said what to do on overflow has to be **clamped to its parent**, which is the reference's `constraints.constrain` in this layer's vocabulary — without it a narrower box never takes the declared width away and the mode never fires. `Fade` is the first use of milestone 339's mask machinery from a widget's paint. **`RichText` caught up in milestone 346** — the same four answers, and nothing in the layout had to change for it, which is the argument for having put `main_axis_floor`, the fill request and the clamp-to-parent where they went rather than inside `Text`. **`softWrap` followed in milestone 344**, and the flag was never the reason it did not: a `Text` declared its own width, and a box that answers before it is asked cannot be told to wrap. It is measured from the space offered now, which needed the other half of the reference's rule — a row never squeezes its inflexible children, a column hands them a width — as `Widget::main_axis_floor`. Eighteen goldens moved by one or two pixels of vertical shift and all eighteen were read.

- ✅ **`truncate` leaves a zero-width box alone — done, milestone 347.** The exception was inherited from the app bar, whose title room has a floor of 64 px and cannot produce a zero in the first place; what it actually did was let a genuinely collapsed box draw its whole label over whatever was beside it, which is the one thing ellipsising exists to prevent. A box with no room gets an ellipsis and nothing else now, and the test that pinned the old behaviour says so.

### Framework depth

- 🟡 **Text rendering edge cases.** Bidi runs, complex scripts, font fallback chains, emoji, vertical metrics. Real bug reports welcome here.
- 🟢 **`Scaffold` and `body` — reviewed, milestone 288.** `extend_body`, `extend_body_behind_app_bar`, `resize_to_avoid_bottom_inset`, `window_insets`, a leading `drawer` beside the trailing one, and `persistent_footer`. The FAB gained a **location** in milestone 290 — three ends × float or docked.

- 🟢 **The renderer composites in scene order — done, milestones 294 and 295.** It used to draw one pass per kind — rectangles, then images, then paths, then text — so *every* path covered *every* rectangle in the frame, wherever the two sat in the scene. - 🟢 **Scrolling physics — done, with two loose ends.** `ScrollPhysics::{Bouncing, Clamping}` with the platform's own fling curves, a real rubber band and per-app / per-area overrides (`docs/milestone-277.md`); a fitted velocity estimate (`docs/milestone-278.md`); the overscroll glow, device-verified (`docs/milestone-279.md`) and rebuilt as an actual **fade** in milestones 301 and 302 after a second device report — it was a flat fill, and a hard curved edge across the page reads as the page being bent rather than as light. - 🟢 **Cache text measurement — done, milestone 300.** Milestone 299 found that **three quarters of the cost of building a frame was `frus_text::measure`**, re-shaping every string through cosmic-text on every call for strings that had not changed. ### Developer experience

- 🔴 **DevTools.** `inspector.rs` can already dump the widget tree. A live inspector — tree view, layout overlay, rebuild counts, frame timing — is a large but very high-leverage project.
- 🟡 **Better error messages.** Layout and constraint failures should say what went wrong and what to change, not just produce a wrong-looking screen.
- 🔴 **A `frus` command-line tool, and hot reload under it.** The architecture below is
  recorded here **before any of it is written**, so that the shape is argued once rather
  than discovered halfway through.

  **What already exists.** `crates/frus-shell/src/reload.rs`: in a debug build, under
  `FRUS_WATCH=1`, the shell watches the mtime of its own executable; when it changes, it
  asks the application for its state (`Application::save_state`), relaunches, and hands the
  bytes back (`restore_state`). That is a **full restart with state preserved**, and it is
  the rung every other rung falls back to. It needs no stable ABI and no tooling of ours:
  `FRUS_WATCH=1 cargo watch -x build` and the running app replaces itself.

  What is missing, in the order it should be built:

  - 🟡 **A `frus` binary.** The framework has no command of its own; everything is
    `cargo` plus environment variables that a newcomer has to be told about. `frus run`,
    `frus dev`, `frus build`, `frus release`, `frus test`, `frus analyze`, `frus doctor` —
    each a thin, honest wrapper that shells out to what already works, and `doctor`
    checking the toolchain, the Android SDK/NDK, `adb`, and the wasm target.
  - 🟡 **A source watcher.** The exe watch reacts only *after* a build someone else
    started. Watching `src/**` and the asset directories, debounced, is what turns two
    commands into one. It belongs in the tool, not in the shell.
  - 🟡 **A `Compiler` abstraction, with `CargoCompiler` as its only implementation.**
    `cargo build --message-format=json` gives structured diagnostics; parsing them is what
    lets the tool report a build failure without a wall of text, and lets the dev loop know
    whether to restart at all.
  - 🔴 **A typed dev protocol.** A `DevCommand` / `DevEvent` channel between the tool
    and the running application over a **loopback-only** socket, so the tool can ask for a
    restart, a state dump, or a widget tree instead of only killing a process. This is also
    DevTools' transport; it should be designed once, for both, or it will be designed twice.
  - 🔴 **Hot reload proper, as three rungs.** Full restart (exists) → **hot restart**
    (same process, fresh state, tree rebuilt from the root) → hot reload (code swapped,
    state kept). The framework half of the third rung is small — the reference locks the
    event queue, flushes its caches and rebuilds from the root (`binding.dart:701`) — and
    the hard half is entirely the code swap, which **has no safe answer in Rust today**:
    there is no stable dynamic ABI, so a `dylib` swap is sound only when both sides come
    from the same compiler with the same flags in the same run. Debug-only, opt-in, and
    never promised as a supported feature. **Hot restart is the honest next rung**, and it
    is worth having on its own.

## Long term

The original brief aims at a full framework, not just a UI toolkit. These are real goals, not yet real work:

- **Plugin system** — a stable ABI for third-party platform integrations (camera, sensors, storage), with the thin-native-adapter rule enforced.
- **FFI story** — embedding frus in an existing native app, and calling native code from frus.
- **Package/ecosystem conventions** — how a community widget library is published and discovered.
- **Static analysis** — lints specific to frus's architecture (impure `update`, hardcoded styling, misplaced platform code).
- **Documentation site** — the milestone notes are excellent raw material, but they are unindexed and unsearchable outside `grep`.

---

## Non-goals

Stated so nobody spends a weekend on them:

- **A DSL or markup language.** Rust with builder methods and the `column!`/`row!` macros is the API. No `.frus` files, no macro that reinvents syntax.
- **A bespoke CLI.** `cargo` is the tool. `cargo generate`, `cargo apk`, `wasm-bindgen` are existing tools; we don't wrap them in `frus doctor`.
- **A software rasterizer.** `wgpu` covers every target we care about.
- **Framework logic in another language.** Non-Rust code is limited to thin platform adapters with no logic of their own.
- **Cloning another framework's API surface verbatim.** We port what works and fix what doesn't. "Framework X does it this way" is a starting point in a discussion, not an argument that ends one.

## How to pick something up

1. Find an item here or in [issues](https://github.com/KalybosPro/frus/issues).
2. Comment saying you're taking it. If there's no issue, open one first — especially for 🔴 items.
3. Read the relevant part of [ARCHITECTURE.md](ARCHITECTURE.md) and `grep docs/` for prior decisions in that area.
4. Build it, test it, and follow [CONTRIBUTING.md](CONTRIBUTING.md).

Small first PRs are welcome and are the fastest way to learn the codebase's conventions. So is an issue that just says "this API is worse than the one I'm used to, here's why" — that is useful work.
